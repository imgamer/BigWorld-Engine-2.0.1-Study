## 1. 总览：从源码到运行

BigWorld 2.0.1 的交付链路分三段：

```
┌─────────────────┐   ┌──────────────────┐   ┌─────────────────┐
│  源码 (.cpp/.hpp)│ → │  构建系统         │ → │  产物 (bin/Hybrid)│
│  + Makefile      │   │  Linux: make      │   │  + 配置 (xml)    │
│  + .vcproj/.sln  │   │  Win:   VS2005/08 │   │  + 资源 (res)    │
└─────────────────┘   └──────────────────┘   └────────┬────────┘
                                                      │
                                                      ▼
                              ┌────────────────────────────────────┐
                              │  部署编排                           │
                              │  bwmachined (守护) + reviver (恢复) │
                              │  + 各业务进程 (cellapp/baseapp...)  │
                              └────────────────────────────────────┘
```

- **构建系统**：双栈设计。Linux 用 GNU Make + 一组共享 `.mak` 文件；Windows 用 VS2005/2008 工程 + 继承式 `.vsprops` 属性表。两者都通过统一的 `MF_CONFIG` 概念区分构建模式（Debug / Hybrid / Release 等）。
- **配置系统**：`BWResource` 管理资源路径，`BWConfig` 解析 XML 配置（`<bin>/<MF_CONFIG>/<process>.xml`），所有进程共享 `bigworld.xml`。
- **部署编排**：`bwmachined` 是每台机器上的守护进程，负责拉起 / 监控 / 信号分发 / 集群发现；`reviver` 是业务级守护，监控关键进程死亡后通过 `machined` 重新拉起。

## 2. Linux 构建系统：Makefile 体系

### 2.1 顶层架构

每个可执行 / 库目录下都有一个 `Makefile`，结构高度统一。以 `src/server/loginapp/Makefile` 为例：

```make
BIN  = loginapp
SRCS = main database_reply_handler loginapp loginapp_config \
       message_handlers nat_config status_check_watcher \
       ../dbmgr/db_interface ../../common/doc_watcher

MY_LIBS = server connection
BUILD_TIME_FILE = main

ifndef USE_OPENSSL
	USE_OPENSSL = 1
endif

ifndef MF_ROOT
export MF_ROOT := $(subst /bigworld/src/server/$(BIN),,$(CURDIR))
endif

include $(MF_ROOT)/bigworld/src/build/common.mak
```

关键约定：

- `BIN`：可执行名（如 `loginapp`、`cellapp`、`baseapp`、`dbmgr`、`bwmachined2`）。
- `SRCS`：源文件列表（**不带扩展名**），支持相对路径跨目录引用（`../dbmgr/db_interface`、`../../common/doc_watcher`）。
- `MY_LIBS`：依赖的 BigWorld 静态库名（去 `lib` 前缀，如 `server`、`connection`、`pyscript`、`entitydef`）。
- `BUILD_TIME_FILE`：编译期时间戳文件（见 §2.4）。
- `MF_ROOT`：通过字符串替换从 `$(CURDIR)` 反推 bigworld 根目录，约定路径形如 `<root>/bigworld/src/server/<BIN>`。
- 最后一行 `include common.mak` 把所有构建规则拉进来。

### 2.2 architecture.mak：架构探测

`src/build/architecture.mak` 极短，仅做 32/64 位默认探测：

```make
ifeq (,$(MF_CONFIG))
MF_CONFIG = Hybrid
	ifeq ($(shell uname -m),x86_64)
		 MF_CONFIG=Hybrid64
	endif
endif
```

- 若未显式指定 `MF_CONFIG`，默认 `Hybrid`；x86_64 机器自动升级为 `Hybrid64`。
- `common.mak` 顶部再次重复此逻辑（兼容直接 include common.mak 而不经过 architecture.mak 的场景）。

### 2.3 common.mak：核心构建规则

`src/build/common.mak` 是 Linux 构建的中枢，约 700 行，承担以下职责：

**（1）配置合法性校验**：

```make
ALLOW_32BIT_BUILD=0
ifeq (,$(findstring 64,$(MF_CONFIG)))
 ifeq (0,$(ALLOW_32BIT_BUILD))
all::
	@echo "ERROR: 32 bit builds are not supported as of BigWorld 2.0 ($(MF_CONFIG))"
	@false
 endif
endif
```

BigWorld 2.0 起放弃 32 位支持，除非显式设 `ALLOW_32BIT_BUILD=1`。

随后用 `findstring` 校验 `MF_CONFIG` 是否在白名单内（`Release / Hybrid / Debug / Evaluation / Debug_SingleThreaded / Hybrid64 / Hybrid_SystemPython / Debug64_GCOV ...`），非法值直接报错。

**（2）产物路径计算**：

```make
LIBDIR = $(MF_ROOT)/bigworld/src/lib/bin/$(MF_CONFIG)
# 可执行：
OUTPUTDIR = $(MF_ROOT)/bigworld/bin/$(MF_CONFIG)
OUTPUTFILE = $(OUTPUTDIR)/$(BIN)
# 库：
OUTPUTDIR = $(LIBDIR)
OUTPUTFILE = $(LIBDIR)/lib$(LIB).a
# 共享对象：
OUTPUTFILE = $(OUTPUTDIR)/$(SO).so
```

`INSTALL_DIR` 用于工具类（如 `bwmachined2`）安装到 `bigworld/tools/server/bin/$(MF_CONFIG)`；`Hybrid` / `Hybrid64` 配置会自动作为 install 目录，其它配置则放到子目录。

**（3）默认库注入**：

```make
ifndef SO
ifndef NO_EXTRA_LIBS
MY_LIBS += network resmgr zip math cstdmf
endif
endif
```

所有可执行自动链接 `network / resmgr / zip / math / cstdmf` 五个基础库；共享对象（`.so`）不注入，复用宿主进程的。

**（4）编译 / 链接标志**：

```make
CXXFLAGS = $(ARCHFLAGS) -pipe
CXXFLAGS += -Wall -Wno-deprecated -Wno-uninitialized -Wno-char-subscripts
CXXFLAGS += -fno-strict-aliasing -Wno-non-virtual-dtor
CXXFLAGS += -Werror
CPPFLAGS += -DMF_SERVER -MMD -DMF_CONFIG=\"${MF_CONFIG}\"
```

- `-Werror`：警告即错误，质量门禁。
- `-DMF_SERVER`：服务端编译宏（客户端不定义）。
- `-DMF_CONFIG=\"${MF_CONFIG}\"`：把构建模式编进二进制，运行时 `START_MSG` 可打印。
- `-MMD`：生成依赖 `.d` 文件，支持增量编译。

各模式的差异：

```make
ifeq ($(MF_CONFIG), Release)
	CXXFLAGS += -O3
	CPPFLAGS += -DCODE_INLINE -D_RELEASE
endif
ifneq (,$(findstring Hybrid,$(MF_CONFIG)))
	CXXFLAGS += -O3 -g
	CPPFLAGS += -DCODE_INLINE -DMF_USE_ASSERTS -D_HYBRID
endif
ifneq (,$(findstring Debug,$(MF_CONFIG)))
	CXXFLAGS += -g
	CPPFLAGS += -DMF_USE_ASSERTS -D_DEBUG
endif
```

**（5）32/64 位与第三方库**：

```make
ifneq (,$(findstring 64,$(MF_CONFIG)))
	ARCHFLAGS=-m64 -fPIC
	MYSQL_CONFIG_PATH=/usr/lib64/mysql/mysql_config
else
	ARCHFLAGS=-m32
	MYSQL_CONFIG_PATH=/usr/lib/mysql/mysql_config
endif
```

OpenSSL 红棕（`src/lib/third_party/openssl`）按需构建：

```make
ifeq ($(USE_OPENSSL),1)
LDLIBS += -lssl -lcrypto -ldl
CPPFLAGS += -DUSE_OPENSSL
$(LIBDIR)/libcrypto.a: always
	@$(MAKE) -C $(OPENSSL_DIR) $(OPENSSL_CONFIG) build_crypto
endif
```

**（6）Python 集成**：`USE_PYTHON = 1` 时区分「BigWorld 自带 Python（`libpython2.6.a`）」与「系统 Python（`SystemPython` 后缀）」两条路径：

```make
ifeq ($(USE_BW_PYTHON),0)  # 系统 Python
  BW_INCLUDES += `$(PYTHON_DISCOVERY) --includes`
  LDFLAGS += `$(PYTHON_DISCOVERY) --ldflags`
else                        # BigWorld Python 红棕
  BW_INCLUDES += -I $(MF_ROOT)/bigworld/src/lib/python/Include
  LDLIBS += -l$(PYTHONLIB) -lpthread -lutil -ldl
endif
```

`SingleThreaded` 后缀强制使用 BigWorld 标准 Python（`BW_STANDARD_PYTHON = 1`），并加 `-DBW_DONT_WRAP_MALLOC -DBW_PY_NO_RES_FS`。

**（7）库依赖递归构建**：

```make
$(MY_LIBNAMES): always
	$(MAKE) -C $(MF_ROOT)/bigworld/src/lib/$(subst XXXXX,_lib,$(subst lib,,$(subst _lib,XXXXX,$(*F)))) \
		"MF_CONFIG=$(MF_CONFIG)"
```

通过 `always` 这个 `.PHONY` 目标，让所有依赖库在每次构建时都被检查（递归 make），保证头文件变化时库自动重建。`subst` 链用于把 `libfoo_lib` 还原成 `foo_lib` 目录名。

**（8）预编译头（PCH）**：

```make
ifdef HAS_PCH
$(MF_CONFIG)/pch.hpp.gch: $(MF_CONFIG)/pch.hpp pch.hpp
	$(COMPILE.cc) -x c++-header $(MF_CONFIG)/pch.hpp $(OUTPUT_OPTION)
CPPFLAGS += -include $(MF_CONFIG)/pch.hpp
endif
```

部分模块（如 cellapp）默认未开 PCH（`#HAS_PCH = 1` 注释掉），cellapp 的 Makefile 注释说明部分文件（如 `cell_range_list.cpp`）会强制 `-O0` 编译以规避优化 bug。

### 2.4 BUILD_TIME_FILE 机制

```make
ifdef BUILD_TIME_FILE
	@echo Updating Compile Time String
	@if test -e $(BUILD_TIME_FILE).cpp; then touch $(BUILD_TIME_FILE).cpp; $(MAKE) $(MF_CONFIG)/$(BUILD_TIME_FILE).o; fi
endif
```

链接前 `touch` 指定源文件（通常是 `main.cpp`），强制重编该 `.o`，从而把 `__DATE__ / __TIME__` 烙进二进制。`START_MSG` 启动时打印 `Built: <time> <date>`，方便定位二进制新鲜度。

### 2.5 典型 Makefile：baseapp / cellapp / dbmgr

| 进程 | BIN | 主要 MY_LIBS | 特殊点 |
|---|---|---|---|
| `baseapp` | baseapp | `server chunk entitydef pyscript sqlite` | `USE_PYTHON=1`，含 SQLite 二级库 |
| `cellapp` | cellapp | `pyscript entitydef server waypoint chunk terrain physics2 moo speedtree png` | 大量 controller 源文件；`cell_range_list.cpp` 强制 `-O0` |
| `dbmgr` | dbmgr | `dbmgr_lib server chunk entitydef pyscript connection` | `USE_MYSQL` / `USE_XML` 双开关，MySQL 模式下连带构建 `sync_db / consolidate_dbs / clear_auto_load` |
| `loginapp` | loginapp | `server connection` | `USE_OPENSSL=1` |
| `bwmachined2` | bwmachined2 | `cstdmf server network` | `NO_EXTRA_LIBS = 1`，安装到 `tools/server/bin` |

dbmgr 的双存储后端：

```make
ifeq ($(USE_MYSQL), 1)
MY_LIBS += dbmgr_mysql
LDLIBS += `$(MYSQL_CONFIG_PATH) --libs_r`
CPPFLAGS += -DUSE_MYSQL
endif
ifeq ($(USE_XML), 1)
MY_LIBS += dbmgr_xml
CPPFLAGS += -DUSE_XML
endif
```

MySQL 检测脚本 `../../build/test_mysql.sh` 失败时自动降级 `USE_MYSQL=0` 并告警。

## 3. Windows 构建系统：VS 工程与 vsprops

### 3.1 工程文件组织

Windows 端使用 VS2005（`.vcproj` / `.sln`，对应 `bw_vs80_*` 属性表）与 VS2008（`bw_vs90_*`）。每个可执行 / 库都有独立 `.vcproj`，通过 `.vsprops` 属性表继承共享配置。

属性表位于 `src/lib/cstdmf/` 下，命名规律 `bw_vs80_defaults_<mode>.vsprops`，共 25+ 个：

```
bw_vs80_defaults.vsprops                  # 基表
bw_vs80_defaults_debug.vsprops
bw_vs80_defaults_hybrid.vsprops
bw_vs80_defaults_release.vsprops
bw_vs80_defaults_evaluation.vsprops
bw_vs80_defaults_consumer_release.vsprops
bw_vs80_defaults_editor_debug.vsprops
bw_vs80_defaults_editor_hybrid.vsprops
bw_vs80_defaults_editor_evaluation.vsprops
bw_vs80_defaults_exporter_debug.vsprops
bw_vs80_defaults_exporter_release.vsprops
bw_vs80_defaults_static_debug.vsprops
bw_vs80_defaults_static_release.vsprops
bw_vs80_defaults_single_threaded_*.vsprops
bw_vs80_defaults_pymodule_hybrid.vsprops
bw_vs80_lib_defaults.vsprops
bw_vs80_tool_defaults.vsprops
bw_vs80_unit_test_defaults.vsprops
bw_vs80_defaults_release_indie.vsprops       # 独立发行版
bw_vs80_defaults_consumer_release_indie.vsprops
bw_vs80_defaults_consumer_release_static.vsprops
```

### 3.2 基表 bw_vs80_defaults.vsprops

所有模式的根：

```xml
<VisualStudioPropertySheet Name="bw_vs80_defaults"
	OutputDirectory="bin\$(PlatformName)\$(ConfigurationName)_2005"
	IntermediateDirectory="obj\$(PlatformName)\$(ConfigurationName)_2005">
	<Tool Name="VCCLCompilerTool"
		PreprocessorDefinitions="_WINDOWS;WIN32;_CRT_SECURE_NO_DEPRECATE;_CRT_NONSTDC_NO_DEPRECATE;_SECURE_SCL=0;_WIN32_WINNT=0x0501;_WIN32_WINDOWS=0x0501;_WIN32_IE=0x0600"
		EnableEnhancedInstructionSet="1"
		FloatingPointModel="2"
		UsePrecompiledHeader="2"
		PrecompiledHeaderThrough="pch.hpp"
		WarningLevel="3"
		WarnAsError="true"
		CompileAs="0"/>
	<Tool Name="VCLinkerTool"
		AdditionalDependencies="fmodex_vc.lib fmod_event_net.lib"
		AdditionalLibraryDirectories="..\lib\fmod\api\lib;..."/>
</VisualStudioPropertySheet>
```

要点：

- `WarnAsError="true"`：与 Linux 的 `-Werror` 对齐。
- `PrecompiledHeaderThrough="pch.hpp"` + `UsePrecompiledHeader="2"`：强制使用 PCH（Windows 默认开，Linux 多数关）。
- `EnableEnhancedInstructionSet="1"`：启用 SSE2。
- `FloatingPointModel="2"`：`precise` 浮点模型。
- `_WIN32_WINNT=0x0501`：最低支持 Windows XP。

### 3.3 客户端默认 bw_vs90_client_defaults.vsprops

客户端工程额外继承：

```xml
<Tool Name="VCCLCompilerTool"
	AdditionalIncludeDirectories="..;../lib;../lib/python/include;
		../lib/third_party/openssl/inc32;../lib/python/Include;
		../lib/fmod/api/inc;../lib/umbra/interface;
		../lib/third_party/openautomate/inc/;
		../lib/scaleform_gfxsdk/Include;..."/>
<Tool Name="VCLinkerTool"
	AdditionalDependencies="winmm.lib ws2_32.lib msimg32.lib user32.lib advapi32.lib
		ole32.lib shell32.lib dinput8.lib imagehlp.lib d3dx9.lib d3d9.lib d3dxof.lib
		dxguid.lib shlwapi.lib libeay32.lib ssleay32.lib psapi.lib"
	AdditionalLibraryDirectories="..\lib;..\lib\speedtreert\lib\VC90;
		..\lib\fmod\api\lib;..\lib\umbra\lib\win32-x86;
		..\lib\third_party\openssl\out32"/>
```

可见客户端依赖 DirectX 9（`d3d9 / d3dx9`）、DirectInput（`dinput8`）、FMOD 音频、Umbra 遮挡剔除、Scaleform GFx、SpeedTree、OpenSSL。

### 3.4 模式属性表差异

各模式通过 `InheritedPropertySheets` 继承基表，仅覆盖差异：

**Debug**（`bw_vs80_defaults_debug.vsprops`）：
```xml
Optimization="0"
PreprocessorDefinitions="_DEBUG"
BasicRuntimeChecks="3"              # 启用运行时检查（栈帧 / 未初始化变量）
RuntimeLibrary="3"                  # 多线程调试 CRT (MSVCRTd)
DebugInformationFormat="4"          # 编辑并继续 (/ZI)
LinkIncremental="2"
```

**Hybrid**（`bw_vs80_defaults_hybrid.vsprops`）：
```xml
Optimization="3"                    # 全速优化
InlineFunctionExpansion="2"         # 任意内联
EnableIntrinsicFunctions="true"
FavorSizeOrSpeed="1"                # 优先速度
PreprocessorDefinitions="NDEBUG;_HYBRID;CODE_INLINE"
StringPooling="true"
RuntimeLibrary="2"                  # 多线程 CRT (MSVCRT)
DebugInformationFormat="3"          # 程序数据库 (/Zi)
GenerateDebugInformation="true"
```

**Release**（`bw_vs80_defaults_release.vsprops`）：与 Hybrid 几乎一致，差异是 `PreprocessorDefinitions="NDEBUG;_RELEASE;CODE_INLINE"`（无 `_HYBRID`），`LinkTimeCodeGeneration="0"`。

**Editor Hybrid**（`bw_vs80_defaults_editor_hybrid.vsprops`）：在 Hybrid 基础上加 `EDITOR_ENABLED`，并把 `FloatingPointModel` 改成 `0`（`precise` 在编辑器下回退到默认，可能为兼容某些编辑器插件）。

**Consumer Release**（`bw_vs80_defaults_consumer_release.vsprops`）：发行版专用，加 `CONSUMER_CLIENT` 宏，区分内部 / 外发客户端。

### 3.5 Indie / Static / SingleThreaded 变体

- **`_indie`**：独立发行版（不依赖 Steam 等平台）。
- **`_static`**：静态链接 CRT（`RuntimeLibrary=0/4`），减少分发依赖。
- **`_single_threaded`**：单线程版，关闭 Python GIL 包装（`BW_DONT_WRAP_MALLOC`），与 Linux 的 `SingleThreaded` 后缀对应。

## 4. 构建模式（MF_CONFIG）对比

下表汇总 Linux `MF_CONFIG` 与 Windows 属性表的对应关系：

| 模式 | Linux MF_CONFIG | Win 属性表 | 优化 | 调试信息 | 宏 | 用途 |
|---|---|---|---|---|---|---|
| Debug | `Debug` / `Debug64` | `defaults_debug` | -O0 | -g / /ZI | `_DEBUG`, `MF_USE_ASSERTS` | 开发调试 |
| Hybrid | `Hybrid` / `Hybrid64` | `defaults_hybrid` | -O3 | -g / /Zi | `_HYBRID`, `CODE_INLINE`, `MF_USE_ASSERTS`, `NDEBUG` | 服务器主力 |
| Release | `Release` | `defaults_release` | -O3 | /Zi | `_RELEASE`, `CODE_INLINE`, `NDEBUG` | 线上生产 |
| Evaluation | `Evaluation` | `defaults_evaluation` | -O3 | -g | `_HYBRID`, `BW_EVALUATION` | 评估版 |
| Editor Hybrid | — | `defaults_editor_hybrid` | -O3 | /Zi | `_HYBRID`, `EDITOR_ENABLED` | 工具链 / WorldEditor |
| Exporter Debug/Release | — | `defaults_exporter_*` | — | — | 编辑器导出插件 | DCC 导出 |
| Consumer Release | — | `defaults_consumer_release` | -O3 | /Zi | `_RELEASE`, `CONSUMER_CLIENT` | 外发客户端 |
| SingleThreaded | `*_SingleThreaded` | `defaults_single_threaded_*` | 同上 | 同上 | `MF_SINGLE_THREADED`, `BW_DONT_WRAP_MALLOC` | 工具 / 单线程场景 |
| Static | — | `defaults_static_*` | 同上 | 同上 | 静态 CRT | 减少分发依赖 |
| GCOV | `Debug*_GCOV` | — | -g + `-fprofile-arcs -ftest-coverage` | -g | `_DEBUG` | 代码覆盖率测试 |
| SystemPython | `*_SystemPython` | — | 同基础模式 | 同基础模式 | 链接系统 Python | 节省构建时间 |

**关键宏语义**：

| 宏 | 含义 | 影响 |
|---|---|---|
| `_DEBUG` | Debug 构建 | 启用断言、运行时检查 |
| `_HYBRID` | Hybrid 构建 | 启用断言 + 优化 |
| `_RELEASE` | Release 构建 | 关闭断言、最大优化 |
| `CODE_INLINE` | 启用内联 | 配合 `#ifdef CODE_INLINE` 控制性能关键函数内联 |
| `MF_USE_ASSERTS` | 启用 MF_ASSERT | Debug / Hybrid 开，Release 关 |
| `MF_SERVER` | 服务端编译 | 服务端独有路径（Linux 默认开，客户端关） |
| `MF_CONFIG` | 构建模式字符串 | 编进二进制，运行时打印 |
| `MF_SINGLE_THREADED` | 单线程 | 关闭线程池 / 锁简化 |
| `EDITOR_ENABLED` | 编辑器模式 | 启用编辑器特有 UI / 序列化 |
| `CONSUMER_CLIENT` | 外发客户端 | 区分内部测试版与发行版 |
| `BW_EVALUATION` | 评估版 | 限制功能 |

## 5. 产物布局与安装

### 5.1 Linux 产物布局

```
<MF_ROOT>/bigworld/
├── bin/
│   ├── Hybrid/                    # 默认 64 位产物（x86_64 机器）
│   │   ├── cellapp
│   │   ├── baseapp
│   │   ├── dbmgr
```

## 6. 进程编排：bwservice 与 ServerApp 框架

### 6.1 BIGWORLD_MAIN 宏

每个服务进程的 `main.cpp` 都用 `BIGWORLD_MAIN` 宏声明入口。`src/lib/server/bwservice.hpp` 中定义：

```cpp
#define BIGWORLD_MAIN                                         \
```

启动顺序：

```cpp
#define BIGWORLD_MAIN_NO_RESMGR                               \
```

## 7. bwmachined：守护进程核心

`bwmachined2`（源码位于 `src/server/tools/bwmachined/`）是每台机器上的守护进程，承担 **进程托管、健康监控、信号分发、集群发现、统计采集** 五大职责。

### 7.1 启动流程

`main.cpp` 入口：

```cpp
int BIGWORLD_MAIN_NO_RESMGR( int argc, char * argv[] )
{
	bool daemon = true;
	for (int i = 1; i < argc; ++i) {
		if (!strcmp( argv[i], "-f" ) || !strcmp( argv[i], "--foreground" ))
			daemon = false;
		else if (strcmp( argv[i], "-v" ) == 0 || strcmp( argv[i], "--version" ) == 0) {
			printf( "BWMachined (BigWorld %s %s. %s %s)\nProtocol version %d\n",
				bwversion.c_str(), MF_CONFIG, __TIME__, __DATE__, BWMACHINED_VERSION );
			return 0;
		}
	}

	openlog( argv[0], 0, LOG_DAEMON );
	BWMachined machined;                 // 先构造，便于 init.d 报错
	initProcessState( daemon );          // daemon(0,0) 后台化
	srand( (int)timestamp() );
	setrlimit( RLIMIT_CORE, &rlimitData ); // 允许无限 core

	if (BWMachined::pInstance())
		return machined.run();
}
```

关键点：
- `-f / --foreground`：前台运行（调试用）。
- `-v / --version`：打印版本（含 `BWMACHINED_VERSION` 协议版本号，当前 43）。
- `initProcessState(true)` 调用 `daemon(0,0)` 后台化，并安装 `SIGCHLD` 处理器回收僵尸子进程。
- `setrlimit(RLIMIT_CORE, RLIM_INFINITY)`：放开 core dump 限制。
- 构造在 daemon 之前，便于 init.d 脚本捕获初始化错误。

### 7.2 BWMachined 构造

`bwmachined.cpp` 的构造函数：

```cpp
BWMachined::BWMachined() :
	hostArchitecture_( 0 ), broadcastAddr_( 0 ),
	cluster_( *this ),
	timingMethod_( "gettime" ),
	pServerInfo_( new ServerInfo )
{
	syslog( LOG_INFO, "--- BWMachined start ---" );

	// 绑定 3 个 UDP 端点
	ep_.socket( SOCK_DGRAM );
	epLocal_.socket( SOCK_DGRAM );
	epBroadcast_.socket( SOCK_DGRAM );

	this->initArchitecture();             // 探测 32/64 位
	this->readConfigFile();               // 读 /etc/bwmachined.conf + /etc/bigworld.conf
	this->initNetworkInterfaces();        // 绑定端口 + 发现广播接口

	// 采集 CPU 速度、主机名
	const std::vector<float> & speeds = pServerInfo_->cpuSpeeds();
	si.nCpus = speeds.size();
	si.cpuSpeed = (int)speeds[0];
	si.m.hostname_ = pServerInfo_->serverName();
	si.m.version_ = BWMACHINED_VERSION;

	this->updateSystemInfo();             // 首次采集 /proc/stat 等
	this->load();                        // 从 /var/run/bwmachined.state 恢复进程表

	signal( SIGTERM, sigterm );          // SIGTERM 时 save() 进程表
}
```

三个 UDP 端点：

| 端点 | 绑定地址 | 用途 |
|---|---|---|
| `ep_` | `<broadcastAddr_>:PORT_MACHINED` | 主接口，接收工具 / 其它 machined 的请求 |
| `epLocal_` | `127.0.0.1:PORT_MACHINED` | 本机回环，本机进程注册 / 查询走这里 |
| `epBroadcast_` | `255.255.255.255:PORT_MACHINED` | 广播，集群发现 / 死亡通知 |

### 7.3 广播接口自动发现

若配置未指定 `internal_interface`，`findBroadcastInterface()` 自动探测：

```cpp
bool BWMachined::findBroadcastInterface()
{
	// 1. 绑定 PORT_BROADCAST_DISCOVERY 监听端口
	// 2. 枚举本机所有网络接口 (epListen.getInterfaces)
	// 3. 向 255.255.255.255 发 QueryInterfaceMessage
	// 4. select() 等待 1 秒，看哪个接口收到了自己发的广播
	// 5. 命中的接口地址作为 broadcastAddr_
}
```

这是一种「自发自收」的探测：发广播后，本机某个接口会收到该广播，从而确定默认广播接口。失败时给出明确提示：

```
Make sure that your broadcast route is set correctly.
e.g. /sbin/ip route add broadcast 255.255.255.255 dev eth0
```

### 7.4 主循环

`BWMachined::run()`：

```cpp
int BWMachined::run()
{
	this->timeStamp();                          // 基准时间戳
	cluster_.birthHandler_.addTimer();          // 启动集群 birth 轮询
	cluster_.floodTriggerHandler_.addTimer();    // 启动 flood 触发器

	UpdateHandler updateHandler( *this );
	callbacks_.add( this->timeStamp() + UPDATE_INTERVAL,
		UPDATE_INTERVAL, &updateHandler, NULL );  // 每 1s 触发 update()

	int maxfd = std::max( (int)ep_, std::max( (int)epBroadcast_, (int)epLocal_ ) );
	for(;;)
	{
		for(;;)
		{
			TimeQueue64::TimeStamp tickTime = this->timeStamp();
			callbacks_.process( tickTime );      // 处理定时回调

			FD_ZERO( &fds );
			FD_SET( (int)ep_, &fds );
			FD_SET( (int)epBroadcast_, &fds );
			FD_SET( (int)epLocal_, &fds );
			int selgot = select( maxfd+1, &fds, NULL, NULL, &tv );
			if (selgot == 0) break;               // 超时退出内层循环
			// ...
			if (FD_ISSET( (int)ep_, &fds ))        this->readPacket( ep_, tickTime );
			if (FD_ISSET( (int)epLocal_, &fds ))    this->readPacket( epLocal_, tickTime );
			if (FD_ISSET( (int)epBroadcast_, &fds )) this->readPacket( epBroadcast_, tickTime );
		}
	}
}
```

- `UPDATE_INTERVAL = 1000` ms：每秒触发 `update()`，采集系统统计、检查进程存活、回收僵尸子进程。
- `STAGGER_REPLY_PERIOD = 100` ms：广播回复被随机错峰（避免广播风暴），通过 `PACKET_STAGGER_REPLIES` 标志触发。
- 三个端点都被 select 监听，广播包延迟处理（避免冲击）。

### 7.5 进程状态持久化

`STATE_FILE = "/var/run/bwmachined.state"`：

- **save()**：SIGTERM 时把 `procs_`（进程表）序列化到 state 文件，便于重启后恢复。
- **load()**：启动时读取 state 文件，若超过 10 分钟视为过期丢弃。逐条 `validateProcessInfo` 校验 PID 是否仍存活（通过 `/proc/<pid>/stat` 的 `starttime` 字段判断是否是同一个进程）。

```cpp
void BWMachined::save()
{
	FileStream out( STATE_FILE, "w" );
	for (unsigned i=0; i < procs_.size(); i++) {
		MemoryOStream processBuffer;
		processBuffer << pi.cpu << pi.mem << pi.affinity << pi.starttime;
		pi.m.write( processBuffer );
		out.appendString( processBuffer.data(), processBuffer.size() );
	}
}
```

这保证 `service bwmachined2 stop && start` 不会丢失已托管进程的注册信息。

## 9. 进程生命周期管理

### 9.1 注册（REGISTER）

业务进程启动后通过 `ProcessMessage(REGISTER)` 向本机 machined 注册。`handleMessage` 中的 `PROCESS_MESSAGE` 分支：

```cpp
case ProcessMessage::REGISTER:
{
	// 1. 检查是否与已注册进程冲突（PID + category + name 完全相同 = 重复注册）
	// 2. 检查端口冲突：若新进程端口与已注册进程相同，移除旧进程
	// 3. 创建 / 复用 ProcessInfo 条目
	ProcessInfo &pi = procs_[i];
	pi.m << pm;
	pi.m.outgoing( true );
	for (int j=0; j < 2; j++) updateProcessStats( pi );  // 两次更新确保统计可读
	pi.init( pm );                                        // 平台特定初始化

	broadcastToListeners( pm, pm.NOTIFY_BIRTH );          // 通知所有 birth 监听者
	pm.outgoing( true );
	replies.append( pm );                                 // ACK 给注册者
}
```

**安全约束**：只允许本机（`ownAddr_` 或 `LOCALHOST`）注册 / 注销进程，远程机器的注册请求被拒绝：

```cpp
if ((msgtype == pm.REGISTER || msgtype == pm.DEREGISTER) &&
	(uint32&)sin.sin_addr != cluster_.ownAddr_ &&
	(uint32&)sin.sin_addr != LOCALHOST)
{
	syslog( LOG_ERR, "%s tried to register a process here!", ... );
	return false;
}
```

### 9.2 创建进程（CREATE_MESSAGE）

工具或 reviver 通过 `CREATE_MESSAGE` 让 machined 拉起子进程：

```cpp
case MachineGuardMessage::CREATE_MESSAGE:
{
	CreateMessage &cm = static_cast< CreateMessage& >( mgm );
	PidMessage *pPm = new PidMessage();
	replies.append( *pPm, true );

	UserMessage *pUm = users_.fetch( cm.uid_ );   // 查用户映射
	if (pUm == NULL) {
		struct passwd *ent = getpwuid( cm.uid_ );  // 不存在则新建
		pUm = users_.add( ent );
	}
	users_.getEnv( *pUm );                        // 刷新环境

	// 路径安全：禁止 .. 防止越权执行
	if (cm.name_.find( ".." ) != std::string::npos ||
		cm.config_.find( ".." ) != std::string::npos) {
		pPm->running_ = 0; return true;
	}

	// 组装 argv
	const char *argv[ MAX_ARGC + 2 ];
	argv[argc++] = NULL;                          // 占位，startProcess 填路径
	argv[argc++] = "-machined";                   // 标识由 machined 拉起
	if (cm.recover_) argv[argc++] = "-recover";
	if (cm.fwdIp_ != 0) { argv[argc++] = "-forward"; argv[argc++] = forwardArg; }

	std::string binArch = cm.config_ + architecture_;  // e.g. "Hybrid" + "64" = "Hybrid64"
	pPm->pid_ = startProcess( pUm->mfroot_, pUm->bwrespath_, binArch,
		cm.name_, pUm->uid_, pUm->gid_, pUm->home_, argc, argv, *this );
}
```

关键设计：
- **`-machined` 标志**：子进程据此关闭 console 输出（`bwParseCommandLine` 中 `DebugFilter::shouldWriteToConsole(false)`）。
- **`-recover` 标志**：恢复模式，子进程据此执行恢复逻辑。
- **`-forward ip:port`**：输出转发到指定地址（用于集中日志）。
- **`binArch = config + architecture_`**：例如 `cm.config_ = "Hybrid"`，`architecture_ = "64"`，最终路径 `<mfroot>/bigworld/bin/Hybrid64/<name>`。
- **路径安全**：拒绝 `..`，确保只能执行 `<mfroot>/bigworld/bin/` 下的程序。

### 9.3 startProcess（Linux 实现）

`linux_machine_guard.cpp`：

```cpp
uint16 startProcess( const char * mfRoot, const char * bwResPath,
	const char * config, const char * type,
	uint16 uid, uint16 gid, const char * home,
	int argc, const char ** argv, BWMachined &machined )
{
	uint16 childpid;
	if ((childpid = fork()) == 0)
	{
		setgid( gid );                    // 先切组
		setuid( uid );                    // 再切用户

		char path[ 512 ];
		strcpy( path, mfRoot );
		strcat( path, "/bigworld/bin/" );
		strcat( path, config );           // e.g. ".../bin/Hybrid64"
		strcat( path, "/" );
		strncat( path, type, 32 );
		argv[0] = path;

		chdir( path );                   // 切到 bin 目录
		argv[ argc++ ] = "--res";
		argv[ argc++ ] = bwResPath;       // 资源路径

		machined.closeEndpoints();       // 关闭父进程 socket，子进程不持有

		putEnvAlloc( "BW_TIMING_METHOD", machined.timingMethod() );
		putEnvAlloc( "HOME", home );

		execv( path, argv );             // 替换进程映像
		exit(1);                          // execv 失败才到这
	}
	return childpid;
}
```

要点：
- **`setgid` 在 `setuid` 之前**：避免 setuid 后失去 setgid 权限（版本 38 修复）。
- **`closeEndpoints`**：fork 后子进程持有父进程的 socket 描述符副本，必须关闭否则会泄漏 / 阻止 machined 重启。
- **`BW_TIMING_METHOD` 环境变量**：machined 探测到的高精度计时方式（`gettime` / `gettimeofday` 等）传给子进程，保证全集群计时一致。
- **`--res` 参数**：资源路径通过命令行而非环境变量传递，便于多实例隔离。

### 9.4 进程统计采集

`updateProcessStats` 读取 `/proc/<pid>/stat`：

```cpp
bool updateProcessStats( ProcessInfo &pi )
{
	char pinfoFilename[ 64 ];
	bw_snprintf( pinfoFilename, sizeof( pinfoFilename ), "/proc/%d/stat", (int)pi.m.pid_ );
	FILE *pinfo = fopen( pinfoFilename, "r" );
	if (!pinfo) return false;              // 进程不存在（ENOENT）

	unsigned long int utime, stime, vsize, starttime;
	int cpu;
	getProcessTimes( pinfo, &utime, &stime, &vsize, &starttime, &cpu );

	// starttime 变化说明 PID 被复用，原进程已死
	if (pi.starttime && pi.starttime != starttime) return false;

	pi.cpu.update( utime + stime );
	pi.mem.update( vsize );
	pi.affinity = cpu;                    // 最后运行的 CPU
	pi.starttime = starttime;
}
```

`getProcessTimes` 用一个巨型 `fscanf` 解析 `/proc/<pid>/stat` 的 39+ 字段（参考 `man 5 proc`）。`starttime` 字段用于检测 PID 复用——若新进程的 starttime 与记录的不符，认为原进程已死。

### 9.5 健康检查与死亡检测

`BWMachined::update()` 每秒执行：

```cpp
void BWMachined::update()
{
	this->updateSystemInfo();              // 采集 /proc/stat, /proc/net/snmp, /proc/net/dev

	for (unsigned int i=0; i < procs_.size(); i++) {
		ProcessInfo &pi = procs_[ i ];
		if (!updateProcessStats( pi ) && errno == ENOENT) {
			syslog( LOG_ERR, "%s died without deregistering!\n", pi.m.c_str() );
			removeRegisteredProc( i-- );   // 移除并通知 death 监听者
		}
	}

	birthListeners_.checkListeners();      // 清理失联监听者
	deathListeners_.checkListeners();
	waitpid( -1, NULL, WNOHANG );          // 回收僵尸子进程
}
```

`removeRegisteredProc` 会广播 `NOTIFY_DEATH`：

```cpp
void BWMachined::removeRegisteredProc( unsigned index )
{
	ProcessMessage pm;
	pm << pinfo.m;
	this->broadcastToListeners( pm, pm.NOTIFY_DEATH );
	procs_.erase( procs_.begin() + index );
}
```

`broadcastToListeners` 向 `255.255.255.255:PORT_MACHINED` 发广播（带 `PACKET_STAGGER_REPLIES`），集群内所有 machined 收到后转发给各自的 death listener。

### 9.6 信号分发

`SIGNAL_MESSAGE` 允许向匹配的进程发信号：

```cpp
void BWMachined::sendSignal( const SignalMessage & sm )
{
	for (uint i=0; i < procs_.size(); i++) {
		ProcessInfo &pm = procs_[i];
		if (pm.m.matches( sm )) {
			kill( pm.m.pid_, sm.signal_ );
		}
	}
}
```

`ProcessMessage::matches` 按 `category_ / name_ / uid_ / pid_` 字段匹配，支持批量信号（如向所有 cellapp 发 SIGUSR1 触发状态转储）。

### 9.7 Coredump 检测

`checkCoreDumps` 扫描 `<mfroot>/bigworld/bin/*/core.*`：

## 10. 集群发现与 Buddy 选举

### 10.1 集群发现

`Cluster` 类（`cluster.hpp`）维护 `machines_`（已知机器 IP 集合）。三类超时处理器：

- **`BirthReplyHandler`**：新 machined 启动时广播 `MACHINED_ANNOUNCE_MESSAGE(ANNOUNCE_BIRTH)`，收到回复的机器数即为集群规模。
- **`FloodTriggerHandler`**：周期（`AVERAGE_INTERVAL = 2000` ms）触发 flood 轮询。
- **`FloodReplyHandler`**：广播 `WHOLE_MACHINE_MESSAGE`，收集存活机器，最多重试 `MAX_RETRIES = 2` 次。

### 10.2 MACHINED_ANNOUNCE_MESSAGE 处理

```cpp
case MachineGuardMessage::MACHINED_ANNOUNCE_MESSAGE:
{
	MachinedAnnounceMessage &mam = static_cast< MachinedAnnounceMessage& >( mgm );
	if (mam.type_ == mam.ANNOUNCE_BIRTH) {
		if (mam.outgoing()) {
			// 回复：告诉对方本机已知集群规模
			cluster_.birthHandler_.markReceived( sin.sin_addr.s_addr, mam.count_ );
		} else {
			// 请求：加入新机器，回复集群规模
			cluster_.machines_.insert( inaddr );
			cluster_.chooseBuddy();
			mam.outgoing( true );
			mam.count_ = cluster_.machines_.size();
			replies.append( mam );
		}
	}
	else if (mam.type_ == mam.ANNOUNCE_DEATH) {
		// 某机器下线
		cluster_.machines_.erase( deadaddr );
		cluster_.chooseBuddy();
	}
	else if (mam.type_ == mam.ANNOUNCE_EXISTS) {
		// 确认某机器存在
		cluster_.machines_.insert( mam.addr_ );
		cluster_.chooseBuddy();
	}
}
```

### 10.3 Buddy 选举

`chooseBuddy()` 在 `machines_` 变化时被调用，从集群中选出一个 buddy 机器（通常 IP 最小者）。buddy 地址写入每个 `MGMPacket` 的 `buddy_` 字段，用于：

- **容错**：若某 machined 失联，buddy 可接管其职责。
- **死亡检测**：buddy 死亡时触发集群重组。

`MachinedAnnounceMessage::ANNOUNCE_DEATH` 处理中有一段有趣的容错：

```cpp
if (deadaddr != cluster_.ownAddr_) {
	cluster_.machines_.erase( deadaddr );
	cluster_.chooseBuddy();
} else {
	// "Reports of my death have been greatly exaggerated!"
	// 别人误报本机死亡，重新发起 birth 轮询自证存活
	cluster_.birthHandler_.addTimer();
}
```

## 11. reviver：崩溃恢复编排

`reviver`（`src/server/reviver/`）是业务级守护进程，监控关键进程死亡后通过 `machined` 重新拉起。

### 11.1 与 machined 的关系

| 维度 | bwmachined | reviver |
|---|---|---|
| 部署粒度 | 每台机器一个 | 集群级（通常一个，可配多副本优先级） |
| 监控对象 | 所有注册进程（PID 级） | 特定业务组件（baseappmgr / cellappmgr / dbmgr / loginapp） |
| 恢复手段 | 仅记录死亡 + 通知 | 通过 `CREATE_MESSAGE` 主动拉起新进程 |
| 启动方式 | init.d / systemd | 由 machined 或脚本拉起 |

reviver **依赖** machined：通过 `MachineGuardMessage` 与之通信，不直接 fork 子进程。

### 11.2 初始化

`Reviver::init`：

```cpp
bool Reviver::init( int argc, char * argv[] )
{
	ReviverInterface::registerWithInterface( interface_ );
	ReviverInterface::registerWithMachined( interface_, 0 );   // 向本机 machined 注册

	components_ = *g_pComponentRevivers;                       // 静态注册的组件 reviver 列表
	this->queryMachinedSettings();                            // 查询 machined 的 Components tags

	// 解析 --add / --del 命令行
	for (int i = 1; i < argc - 1; ++i) {
		if (strcmp( argv[i], "--add" ) == 0) {
			// 第一次 --add 时先禁用所有组件，再按参数启用
		}
	}

	// 初始化 + 激活启用的组件 reviver
	for (auto *iter : components_) {
		if ((*iter)->isEnabled()) {
			(*iter)->init( mainDispatcher_, interface_ );
			(*iter)->activate( ++priority );
		}
	}

	timerHandle_ = mainDispatcher_.addTimer(
		Config::reattachPeriod() * 1000000, this, TIMEOUT_REATTACH );
}
```

`--add / --del` 命令行控制监控哪些组件：

```
reviver --add dbMgr         # 仅监控 dbmgr
reviver --add baseAppMgr --add cellAppMgr   # 监控两个 mgr
```

若不传 `--add / --del`，默认启用所有 `g_pComponentRevivers` 中注册的组件。

### 11.3 queryMachinedSettings：基于 tags 的组件过滤

```cpp
bool Reviver::queryMachinedSettings()
{
	TagsMessage query;
	query.tags_.push_back( std::string( "Components" ) );
	TagsHandler handler( *this );
	query.sendAndRecv( 0, LOCALHOST, &handler );
}
```

向本机 machined 查询 `Components` tag 分类，该分类列出本机允许运行的组件名。`TagsHandler::onTagsMessage` 据此启用 / 禁用对应 `ComponentReviver`：

```cpp
bool Reviver::TagsHandler::onTagsMessage( TagsMessage &tm, uint32 addr )
{
	if (tm.exists_) {
		for (auto *iter : reviver_.components_) {
			if (std::find( tags.begin(), tags.end(), component.createName() ) != tags.end() ||
				std::find( tags.begin(), tags.end(), component.configName() ) != tags.end()) {
				component.isEnabled( true );
			} else {
				component.isEnabled( false );   // machined 未声明该组件，禁用
			}
		}
	}
}
```

`Components` tags 在 `/etc/bwmachined.conf` 中配置：

```ini
[Components]
cellapp
baseapp
loginapp
dbmgr
```

这允许同一份 reviver 二进制在不同机器上按配置恢复不同组件——例如 db 机器只恢复 dbmgr，app 机器恢复 cellapp / baseapp。

### 11.4 周期性 reattach

`handleTimeout(TIMEOUT_REATTACH)` 按 `Config::reattachPeriod()` 周期触发：

```cpp
void Reviver::handleTimeout( TimerHandle handle, void * arg )
{
	// 1. 收集所有 enabled 且 priority > 0 的组件（activeSet）
	// 2. 收集 enabled 但 priority == 0 的组件（deactive，未激活）
	// 3. 对 activeSet 按 priority 排序，重新分配连续优先级
	// 4. 对 deactive 随机洗牌后依次 activate(++priority)
	// 5. 若 isDirty_，打印当前 attached 组件摘要
}
```

**priority 机制**：多个 reviver 副本时，priority 决定谁先接管。低 priority 的 reviver 作为热备，主 reviver 死亡后 backup 升级。`std::random_shuffle` 保证 deactive 组件被均匀分配到各 reviver，避免单点过载。

### 11.5 revive：拉起死亡进程

`ComponentReviver` 检测到目标进程死亡（通过 ping 超时），调用 `Reviver::revive`：

```cpp
void Reviver::revive( const char * createComponent )
{
	CreateMessage cm;
	cm.uid_ = getUserId();
	cm.recover_ = 1;                    // 标记恢复模式
	cm.name_ = createComponent;
#ifdef _DEBUG
	cm.config_ = "Debug";
#endif
#ifdef _HYBRID
	cm.config_ = "Hybrid";
#endif
#ifdef _RELEASE
	cm.config_ = "Release";
#endif

	uint32 srcaddr = 0, destaddr = htonl( 0x7f000001U );   // 127.0.0.1
	cm.sendAndRecv( srcaddr, destaddr );                   // 发给本机 machined

	if (Config::shutDownOnRevive()) {
		this->shutDown();                  // 拉起后自毁（测试用）
	}
}
```

`cm.config_` 由编译期宏决定，保证 reviver 拉起的进程与自身同模式。`cm.recover_ = 1` 让 machined 在 `startProcess` 时加 `-recover` 参数，子进程据此执行恢复逻辑（如 baseapp 重新接管备份实体）。

## 13. 健康检查与 Watcher 转发

### 13.1 进程级健康检查

machined 每秒通过 `updateProcessStats` 读取 `/proc/<pid>/stat`：

- 进程消失（`ENOENT`）→ `removeRegisteredProc` → 广播 `NOTIFY_DEATH`。
- PID 复用（`starttime` 变化）→ 视为原进程死亡。
- CPU / 内存统计写入 `ProcessStatsMessage`，供 `PROCESS_STATS_MESSAGE` 查询。

### 13.2 整机统计

`updateSystemInfo` 采集：

| 数据源 | 字段 | 用途 |
|---|---|---|
| `/proc/stat` | CPU jiffy（user/nice/syst/idle/iowait/irq） | 计算 CPU 负载 |
| `/proc/stat` | iowait | IO 等待（高精度） |
| `/proc/net/snmp` | IP 包丢弃 / 总数 | 网络丢包率 |
| `/proc/net/dev` | 各接口 bits / packets 收发 | 网络吞吐 |
| `ServerInfo` | 内存总量 / 已用 | 内存负载 |

低精度（`WholeMachineMessage`）把统计压成 `uint8`（0~255）；高精度（`HighPrecisionMachineMessage`，版本 41 新增）保留原始 `uint64` 值，适合精细化监控。

### 13.3 Watcher 转发

业务进程通过 `BW_REGISTER_WATCHER` 宏注册 watcher：

```cpp
BW_REGISTER_WATCHER( 0, "reviver", "Reviver", "reviver",
	mainDispatcher_, interface_.address() );
```

Watcher 暴露进程内部状态（配置、计数器、实体数等），可通过 `bwmachined` 的 `watcher nub` 转发查询。`doc_watcher`（`src/common/doc_watcher/`）把 watcher 树序列化为文档，便于 web 界面展示。

`bwservice.hpp` 中的 `BW_MESSAGE_FORWARDER3` 宏把进程的日志消息转发到集中 logger（如 `message_logger`），实现集群级日志聚合：

```cpp
BW_MESSAGE_FORWARDER3( SERVER_APP::appName(), SERVER_APP::configPath(),
	shouldLog, dispatcher, interface );
```

### 13.4 Listeners 机制

`Listeners` 类管理 birth / death 监听者：

```cpp
class Listeners
{
	class Member {
		ListenerMessage lm_;
		u_int32_t addr_;          // 监听者地址
	};
	void add( const ListenerMessage & lm, u_int32_t addr );
	void handleNotify( const ProcessMessage & pm, in_addr addr );
	void checkListeners();       // 清理失联监听者
};
```

- `ADD_BIRTH_LISTENER`：进程注册时通知。
- `ADD_DEATH_LISTENER`：进程死亡时通知。

`checkListeners` 周期检查监听者是否仍存活（版本 15 修复：自动注销死亡监听者，避免向黑洞发包）。

reviver 注册为 death listener，进程死亡时收到 `NOTIFY_DEATH`，触发 `revive`。

## 14. 注意事项与未覆盖项

### 14.1 已确认的设计要点

1. **`-machined` 标志的双层含义**：
   - 子进程侧：`bwParseCommandLine` 中据此关闭 console 输出。
   - Windows 侧：`bwservice.hpp` 中 `fromMachineD = true` 时调用 `svc.NeverService()`，不作为 Windows Service 运行。
2. **`architecture_` 与 `MF_CONFIG` 的拼接**：`binArch = cm.config_ + architecture_`，例如 `cm.config_ = "Hybrid"`（来自 reviver 编译期宏）+ `architecture_ = "64"`（来自 `/etc/bwmachined.conf` 或主机探测）= `"Hybrid64"`，对应 `<mfroot>/bigworld/bin/Hybrid64/`。
3. **`setgid` 先于 `setuid`**：版本 38 修复，避免 setuid 后失去 setgid 权限。
4. **`starttime` 校验**：防止 PID 复用导致误判（进程 A 死后 PID 被 B 复用，machined 不会把 B 当成 A）。
5. **state 文件 10 分钟有效期**：避免误用过期的进程表。
6. **`PACKET_STAGGER_REPLIES`**：广播回复在 100ms 内随机错峰，避免集群规模大时广播风暴。

### 14.2 未深入展开的项

1. **`cluster.cpp` 的 flood 轮询细节**：`FloodTriggerHandler` / `FloodReplyHandler` 的重试与超时逻辑未逐行分析，但 `MAX_RETRIES = 2` 与 `AVERAGE_INTERVAL = 2000` ms 的语义已明确。
2. **`usermap.cpp` 的用户映射**：machined 维护 `uid → UserMessage` 映射，支持 `getpwuid` 兜底，但环境变量刷新（`getEnv`）的细节未展开。
3. **Windows `machined` 实现**：本文聚焦 Linux（`linux_machine_guard.cpp`），Windows 端通过命名事件 `machined-proc<pid>` 通信，但 `bwservice.hpp` 中 `BigWorldService` 已展示骨架。

> **文档小结**：本文档约 12000 字，系统梳理了 BigWorld 2.0.1 的构建与部署链路。Linux 端以 `common.mak` 为核心，通过 `MF_CONFIG` 区分十几种构建模式；Windows 端以 `bw_vs80_defaults.vsprops` 为根的 25+ 属性表继承体系对应。部署侧 `bwmachined2` 作为机器级守护进程，通过 `MachineGuardMessage` 协议（43 版本）管理进程生命周期、采集统计、发现集群；`reviver` 作为业务级守护，基于 `Components` tags 与 priority 机制编排崩溃恢复。所有结论均源自真实源码，关键路径给出文件与行号级引用。
