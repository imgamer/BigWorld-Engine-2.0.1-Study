## 1. 问题背景：脚本驱动的统一对象模型

MMO 服务端的复杂度在于：玩法千变万化、需要不停迭代、且要分摊到 baseapp / cellapp / client 等多种异构进程上。如果全部用 C++ 写死，迭代周期长、部署代价高。BigWorld 的解法是把 **对象模型** 与 **业务逻辑** 解耦：

- **C++ 提供统一的对象模型骨架**：每个游戏对象（Entity）在 C++ 里是一个 `PyObjectPlus` 派生类，自带引用计数、属性表、方法表、网络序列化、定时器、远程调用等基础设施。
- **Python 提供可热更新的业务逻辑**：每种 Entity 类型对应一个 `.py` 模块，模块里定义一个继承自 C++ 类的 Python 类，覆写 `onTimer` / `onEnterTrap` / `__init__` 等回调即可定义行为。
- **同一份 `.def` 描述贯穿所有进程**：`entities.xml` + 每种实体的 `.def` 文件声明了属性、方法、Client/Cell/Base 三个域的分布，由 `EntityDescription` 解析后被所有进程共享。

BigWorld 把这条主线分散在多个进程上：

| 进程 | C++ 对象模型类 | Python 派生基类 | 脚本目录 |
|---|---|---|---|
| cellapp | `Entity : public PyInstancePlus` | `BigWorld.Entity` | `scripts/cell/` |
| baseapp | `Base : public PyInstancePlus` | `BigWorld.Base` | `scripts/base/` |
| client | `Entity : public PyInstancePlus` | `BigWorld.Entity` | `scripts/client/` |
| dbmgr | （无 Entity 实例） | （无） | `scripts/database/` |

本文档沿着「CPython 初始化 → BigWorld 模块诞生 → Personality 入口 → EntityType 加载 .py 类 → 实体创建 → 属性/方法/远程调用 → 定时器 → 客户端生命周期」这条主线展开。

## 2. Python 嵌入架构：每个进程一个 CPython

BigWorld 采用 **嵌入式 CPython**：每个进程（cellapp、baseapp、client、dbmgr、loginapp……）在启动时调用 `Script::init()` 初始化一个 CPython 解释器，并把引擎的各种 C++ 类注册进去。这是一个 **单解释器、多线程加锁** 的模型——`Script::initThread` / `Script::acquireLock` / `Script::releaseLock` 提供线程间共享解释器的锁机制（参见 [script.hpp](file:///workspace/src/lib/pyscript/script.hpp)）。

`Script::init` 的关键步骤（节选自 [script.cpp](file:///workspace/src/lib/pyscript/script.cpp) 第 285 行起）：

```cpp
// /workspace/src/lib/pyscript/script.cpp
bool Script::init( const PyImportPaths & appPaths,
                    const char * componentName,
                    bool shouldOverrideSysMembers )
{
    // 1. 构造 Python 的 sys.path，包含 commonPath、EntityDef 等路径
    PyImportPaths sysPaths( DELIM );
    sysPaths.append( appPaths );
    std::string commonPath( EntityDef::Constants::commonPath() );
    sysPaths.addPath( commonPath );
    sysPaths.addPath( commonPath + "/Lib" );
    // ...

    // 2. 初始化 CPython（关闭 site、忽略环境变量、冻结模块）
    Py_NoSiteFlag = 1;
    Py_IgnoreEnvironmentFlag = 1;
    Py_Initialize();

    // 3. 注入 ResMgrImportHook，让 import 能从 BWResource 文件系统加载
    PyObject* importHook = new PyResMgrImportHook();
    PyList_Append( PySys_GetObject("path_hooks"), importHook );

    // 4. 关闭 GC（性能考虑，引擎自己管理对象生命周期）
    PyObject * pGCModule = PyImport_ImportModule( "gc" );
    PyObject_CallMethod( pGCModule, "disable", NULL );

    // 5. 创建/获取 BigWorld 模块，并写入 BigWorld.component 标识
    PyObject * pBigWorld = PyImport_AddModule( "BigWorld" );
    PyObject * pStr = PyString_FromString( componentName );
    PyObject_SetAttrString( pBigWorld, "component", pStr );

    // 6. 初始化 Pickler（用于跨进程的对象序列化）
    Pickler::init();

    // 7. 导入 BWAutoImport 模块（自动注册常用模块）
    PyImport_ImportModule( "BWAutoImport" );
    return true;
}
```

几个关键点：

- **`componentName`** 是进程自识别标签，被写入 `BigWorld.component`，可能值是 `'cell'` / `'base'` / `'client'` / `'database'` / `'bot'` / `'editor'`。脚本能通过 `BigWorld.component` 判断自己跑在哪种进程里，从而选择不同的行为分支。
- **`PyResMgrImportHook`** 让 `import` 既能从磁盘加载，也能从 BigWorld 的资源包（`.zip`、`.pck`）加载——这对客户端打包发布至关重要。
- **GC 被关闭**：因为 `PyObjectPlus` 派生类完全由 C++ 的 `SmartPointer` 与 Python 引用计数共同管理，循环 GC 反而会干扰。这是 MMO 服务端常见的取舍。
- **`BigWorld` 是一个内置模块**：通过 `PyImport_AddModule("BigWorld")` 创建空模块后，各进程在自己的初始化阶段（如 cellapp 的 `initScript`、client 的 `script_bigworld.cpp`）用 `PY_MODULE_FUNCTION` 等宏向它注入函数与常量。

每个进程注入到 `BigWorld` 模块的内容不同：cellapp 注入 `createEntity` / `addTimer` / `entitiesInRange` 等；baseapp 注入 `createBase` / `createBaseAnywhere` / `writeToDB` 等；client 注入 `createEntity` / `findDropPoint` / `player` 等。脚本看到的是 **同一个 `BigWorld` 命名空间，但 API 集随进程而变**。

## 3. PyObjectPlus：C++ 对象暴露给 Python 的基类

[PyObjectPlus](file:///workspace/src/lib/pyscript/pyobject_plus.hpp) 是 BigWorld 所有「暴露给 Python 的 C++ 类」的根基类。它的注释写得很清楚：

> This is the abstract base class for all Python classes which are implemented in the engine. Every other class inherits, directly or indirectly from PyObjectPlus.

`PyObjectPlus` 直接继承自 CPython 的 `PyObject`，这意味着 **每个 PyObjectPlus 派生类的实例本身就是合法的 `PyObject*`**——这是 BigWorld 对象模型的核心设计：

```cpp
// /workspace/src/lib/pyscript/pyobject_plus.hpp
class PyObjectPlus : public PyObject
{
    Py_Header( PyObjectPlus, PyObjectPlus )
public:
    PyObjectPlus( PyTypeObject * pType, bool isInitialised = false );

    void incRef() const             { Py_INCREF( (PyObject*)this ); }
    void decRef() const             { Py_DECREF( (PyObject*)this ); }
    Py_ssize_t refCount() const     { return ((PyObject*)this)->ob_refcnt; }

    PyObject * pyGetAttribute( const char * attr );
    int pySetAttribute( const char * attr, PyObject * value );
    int pyDelAttribute( const char * attr );
    void pyDel();

    PyObject * pyRepr();
    const char * typeName() const   { return ob_type->tp_name; }

protected:
    ~PyObjectPlus();  // protected：只能由 Python 的引用计数归零触发
};

typedef PyObjectPlus PyInstancePlus;
```

关键设计要点：

1. **多重身份合一**：`PyObjectPlus*`、`PyObject*`、具体派生类指针三者可以 `static_cast` 互转。C++ 代码用派生类指针访问业务字段，Python 解释器用 `PyObject*` 访问引用计数与类型对象——它们指向同一块内存。
2. **protected 析构**：`~PyObjectPlus()` 是 protected，禁止 C++ 代码直接 `delete`。对象只能通过 Python 的 `_tp_dealloc`（在引用计数归零时调用）销毁，这保证了 Python 与 C++ 的生命周期管理不会打架。
3. **`PyInstancePlus` 别名**：`typedef PyObjectPlus PyInstancePlus;`——服务端的 `Base`、`Entity` 都用 `Py_InstanceHeader` 宏声明自己继承自 `PyInstancePlus`，语义上是「可被 Python 实例化的类型」。
4. **弱引用变体**：`PyObjectPlusWithWeakReference` 增加 `weakreflist_`，支持 Python 的 `weakref`；`PyObjectPlusWithVD` 是带虚析构的变体（用于需要多态析构的场景）。

### 3.1 Py_Header 与 Py_InstanceHeader

`Py_Header(CLASS, SUPER_CLASS)` 是每个 `PyObjectPlus` 派生类必须放在第一行的宏，它生成了 CPython 类型对象所需的全部回调：

```cpp
// /workspace/src/lib/pyscript/pyobject_plus.hpp（节选）
#define Py_Header( CLASS, SUPER_CLASS )                                       \
    public:                                                                   \
        static void _tp_dealloc( PyObject * pObj )                            \
        {                                                                     \
            static_cast< CLASS * >( pObj )->pyDel();                          \
            delete static_cast< CLASS * >( pObj );                            \
        }                                                                     \
        static PyObject * _tp_getattro( PyObject * pObj, PyObject * name )    \
        {                                                                     \
            return static_cast<CLASS*>(pObj)->pyGetAttribute(                 \
                    PyString_AS_STRING( name ) );                             \
        }                                                                     \
        static int _tp_setattro( PyObject * pObj, PyObject * name,            \
            PyObject * value )                                                \
        {                                                                     \
            const char * attr = PyString_AS_STRING( name );                   \
            return (value != NULL) ?                                          \
                static_cast<CLASS*>(pObj)->pySetAttribute( attr, value ) :    \
                static_cast<CLASS*>(pObj)->pyDelAttribute( attr );            \
        }                                                                     \
        static PyObject * _tp_repr( PyObject * pObj )                         \
        { return static_cast<CLASS *>(pObj)->pyRepr(); }                      \
    Py_InternalHeader( CLASS, SUPER_CLASS )

#define Py_InstanceHeader( CLASS ) Py_Header( CLASS, PyObjectPlus )
```

- `_tp_dealloc`：引用计数归零时调用，先调 `pyDel()`（派生类可覆写做清理），再 `delete` 自己。
- `_tp_getattro` / `_tp_setattro`：把 Python 的属性访问转发到虚函数 `pyGetAttribute` / `pySetAttribute`，派生类（如 `Base`、`Entity`、`PyEntityMailBox`）通过覆写它们实现自定义属性查找。
- `Py_InstanceHeader(CLASS)` 是 `Py_Header(CLASS, PyObjectPlus)` 的简写，用于「可被 Python 继承/实例化」的类。

### 3.2 属性访问的查找表

`Py_CommonHeader` 宏为每个类生成了一个静态属性表 `s_attributes_`，类型是 `ThisAttributeMap`（一个 `StringHashMap<PyAttributeAccessor>`）。每个 `PY_ATTRIBUTE(NAME)` 宏调用会把 `(pyGet_NAME, pySet_NAME)` 这对函数指针插入表中：

```cpp
// 简化的属性查找逻辑（参见 PY_GETATTR_STD 宏）
ThisAttributeMap::iterator found = s_attributes_.find( attr );
if (found != s_attributes_.end())
{
    return (this->*(*found).second.get)();  // 调用 pyGet_NAME()
}
```

这就是 BigWorld 的「属性系统」——无需手写 `tp_getattr`，只要在类里 `PY_ATTRIBUTE(position)` 就自动暴露了 `position` 属性给 Python。`PyDirInfo` 还会把这些名字填进 `__members__` / `__methods__`，让 `dir(obj)` 能列出。

## 4. Py_Header 与属性/方法声明宏体系

BigWorld 用一组宏把「C++ 类成员」声明为「Python 可见属性/方法」。这套宏是 `PyObjectPlus` 的「语法糖层」，让暴露 API 变得声明式。

### 4.1 属性宏

| 宏 | 含义 |
|---|---|
| `PY_RW_ATTRIBUTE_DECLARE(MEMBER, NAME)` | 读写在 `s_attributes_` 表，绑定到成员变量 |
| `PY_RO_ATTRIBUTE_DECLARE(MEMBER, NAME)` | 只读属性 |
| `PY_WO_ATTRIBUTE_DECLARE(MEMBER, NAME)` | 只写属性 |
| `PY_RW_ACCESSOR_ATTRIBUTE_DECLARE(TYPE, MEMBERFN, NAME)` | 通过 getter/setter 函数访问 |
| `PY_ATTRIBUTE(NAME)` | 在 `PY_BEGIN_ATTRIBUTES` 块里注册属性 |
| `PY_RO_ATTRIBUTE_SET(NAME)` | 把 set 函数实现为「只读报错」 |

底层都靠 `Script::getData` / `Script::setData` 做 C++ 值与 `PyObject*` 的互转。例如 `PY_WRITABLE_ATTRIBUTE_SET` 展开：

```cpp
// /workspace/src/lib/pyscript/pyobject_plus.hpp
#define PY_WRITABLE_ATTRIBUTE_SET( MEMBER, NAME )                             \
    int PY_ATTR_SCOPE pySet_##NAME( PyObject * value )                        \
        { return Script::setData( value, MEMBER, #NAME ); }
```

`Script::setData(PyObject*, T&, const char*)` 是一组重载模板，覆盖了 `int`、`float`、`std::string`、`Vector3`、`Matrix`、`EntityMailBoxRef` 等常见类型——这就是 Python ↔ C++ 的 **基本类型桥**。

### 4.2 方法宏

| 宏 | 含义 |
|---|---|
| `PY_METHOD_DECLARE(NAME)` | 声明一个接收 `PyObject* args` 的方法 |
| `PY_AUTO_METHOD_DECLARE(RET, NAME, ARGS)` | 自动解析参数的便捷版本 |
| `PY_KEYWORD_METHOD_DECLARE(NAME)` | 支持关键字参数 |
| `PY_STATIC_METHOD_DECLARE(NAME)` | 静态方法 |
| `PY_FACTORY_DECLARE()` | 工厂方法（让 Python 能 `BigWorld.Foo()` 创建） |
| `PY_METHOD(NAME)` | 在 `PY_BEGIN_METHODS` 块里注册方法 |

`PY_METHOD_DECLARE(pyCall)` 会生成一个 `pyCall(PyObject* args)` 成员函数和一个静态 trampoline `_pyCall`，后者被注册成 `PyMethodDef`。这是 `RemoteEntityMethod` 实现远程方法调用的关键（见第 14 节）。

### 4.3 类型对象宏

每个 `PyObjectPlus` 派生类在 `.cpp` 里要用 `PY_TYPEOBJECT` / `PY_TYPEOBJECT_WITH_SEQUENCE` 等宏实例化静态类型对象 `s_type_`。这些宏展开成一个完整的 `PyTypeObject`，把 `tp_dealloc` / `tp_getattro` / `tp_setattro` 等都指向宏生成的静态函数，并把 `tp_base` 设为父类的 `s_type_`——这就构成了 BigWorld 的 **C++ 类型继承链**，Python 解释器看到的类型层级与 C++ 完全一致。

最后用 `PY_FACTORY(THIS_CLASS, MODULE_NAME)` 把这个类型注册到指定 Python 模块（通常是 `BigWorld`），让脚本能 `BigWorld.ServerEntityMailBox(...)` 这样构造。

## 5. Script::init 与 BigWorld 模块的诞生

`BigWorld` 是 BigWorld 脚本生态的中枢模块。它不是一个普通的 `.py` 文件，而是一个 **C++ 注入的内置模块**——每个进程在 `Script::init` 之后，通过各自的 `initScript` / `script_bigworld.cpp` 用 `PY_MODULE_FUNCTION` 宏向它注入函数。

### 5.1 模块的创建

`Script::init` 里 `PyImport_AddModule("BigWorld")` 创建了一个空模块对象。之后任何 `import BigWorld` 都会拿到这个对象。各进程的初始化代码再向它的字典里塞函数、常量、类。

### 5.2 函数注入示例（client 端）

以 client 端的 `BigWorld.createEntity` 为例（[script_bigworld.cpp](file:///workspace/src/client/script_bigworld.cpp) 第 1780 行）：

```cpp
// /workspace/src/client/script_bigworld.cpp
static PyObject * py_createEntity( PyObject * args )
{
    char * name; int spaceID; int vehicleID;
    Vector3 pos, dir; PyObject * pDict;
    if (!PyArg_ParseTuple(args, "sii(fff)(fff)O!:BigWorld.createEntity",
            &name, &spaceID, &vehicleID,
            &pos.x, &pos.y, &pos.z,
            &dir.x, &dir.y, &dir.z,
            &PyDict_Type, &pDict ))
    {
        return NULL;
    }
    // ... 找到 EntityType，调用 EntityManager::onEntityCreate ...
    EntityManager::instance().onEntityCreate( id, pType->index(),
        spaceID, vehicleID, pos, dir.x, dir.y, dir.z, stream );
    return PyLong_FromUnsignedLong( id );
}
PY_MODULE_FUNCTION( createEntity, BigWorld )
```

`PY_MODULE_FUNCTION(name, module)` 宏把这个 C 函数注册成 `BigWorld.name`。每个进程注册的函数集合不同，但调用形式统一——这就是为什么同一份脚本可以在不同进程里 `import BigWorld` 然后调用 `BigWorld.addTimer(...)` 而无需关心自己跑在哪。

### 5.3 服务端的 BigWorld 注入

cellapp 与 baseapp 的 `BigWorld` 函数注入由各自的 `initScript()` 完成（参见 [cellapp.hpp](file:///workspace/src/server/cellapp/cellapp.hpp) 第 220 行 `bool initScript();`）。注入的函数包括：

- **cellapp**：`createEntity`、`addTimer`、`delTimer`、`entitiesInRange`、`createEntityFromFile`、`addSpaceGeometryMapping` 等。
- **baseapp**：`createBase`、`createBaseAnywhere`、`createBaseFromDB`、`writeToDB`、`addTimer`、`delTimer` 等。
- **公共**：`BigWorld.component`、`BigWorld.time`、`BigWorld.Spaces`、`BigWorld.dEntityDefs` 等。

注意 `addTimer` / `delTimer` 在 cellapp 和 baseapp 都有，但底层委托给各自的 `ScriptTimers`（见第 16 节）。

## 6. Personality：进程级入口脚本

除了 `BigWorld` 模块，每个进程还有一个 **Personality**（人格）脚本——它代表「这个进程是谁」。`Personality` 命名空间（[personality.hpp](file:///workspace/src/lib/pyscript/personality.hpp) / [personality.cpp](file:///workspace/src/lib/pyscript/personality.cpp)）管理这个全局单例：

```cpp
// /workspace/src/lib/pyscript/personality.hpp
#define DEFAULT_PERSONALITY_NAME "BWPersonality"

namespace Personality
{
extern const char *DEFAULT_NAME;
PyObject* import( const std::string &name );  // 导入人格模块
PyObject* instance();                          // 获取已导入的人格模块
bool callOnInit( bool isReload = false );      // 调用其 onInit
}
```

`Personality::import` 的实现非常简单——就是 `PyImport_ImportModule`：

```cpp
// /workspace/src/lib/pyscript/personality.cpp
PyObject* import( const std::string &name )
{
    if (s_pInstance_) { WARNING_MSG(...); return s_pInstance_; }
    s_pInstance_ = PyImport_ImportModule( const_cast<char*>( name.c_str() ) );
    if (s_pInstance_)
    {
        new PersonalityFiniTimeJob();  // 注册关闭时调用 onFini
    }
    return s_pInstance_;
}

bool callOnInit( bool isReload )
{
    return Script::call( PyObject_GetAttrString( s_pInstance_, "onInit" ),
            PyTuple_Pack( 1, isReload ? Py_True : Py_False ), "onInit", true );
}
```

人格模块约定要提供两个回调：

- `onInit(isReload)`：进程启动（或脚本热重载）时被调用，做全局初始化。
- `onFini()`：进程关闭时被调用，做清理。

不同进程使用不同的人格模块——cellapp 的 `BWPersonality` 通常负责初始化 cellapp 专属的全局状态、注册全局 base、加载世界等。人格是 **进程级** 的单例脚本，与 **实体级** 的 `.py` 模块（每种 Entity 类型一个）形成对照。

`PersonalityFiniTimeJob` 继承自 `Script::FiniTimeJob`，在脚本系统关闭时按 rung 顺序执行——这保证了人格模块的 `onFini` 在所有实体脚本析构之后才被调用。

## 7. EntityType：从 .def 到 Python 类的桥

`EntityDescription` 描述了一种实体类型的 **元数据**（属性、方法、分布域），但它本身不持有 Python 类对象。**把元数据与 Python 类绑定的桥梁是 `EntityType`**——每个进程都有自己的 `EntityType` 类：

### 7.1 EntityDescription：元数据载体

### 7.2 EntityType::init：加载 Python 类

`EntityType::init` 把元数据与 Python 类绑定。以 client 端为例（[entity_type.cpp](file:///workspace/src/client/entity_type.cpp) 第 140 行起）：

```cpp
// /workspace/src/client/entity_type.cpp
for (int i = 0; i < numEntityTypes; i++)
{
    const EntityDescription & currDesc = entityDescriptionMap.entityDescription( i );
    if (!currDesc.isClientType()) continue;

    // 1. 导入与实体同名的 Python 模块，如 Avatar.py
    PyObject * pModule = PyImport_ImportModule(
        const_cast<char*>( currDesc.name().c_str() ) );

    // 2. 从模块里取出与实体同名的类，如 class Avatar(BigWorld.Entity)
    PyObject * pClass = PyObject_GetAttrString( pModule,
        const_cast<char *>( currDesc.name().c_str() ) );

    // 3. 校验：必须是 BigWorld.Entity 的子类
    if (PyObject_IsSubclass( pClass, (PyObject *)&Entity::s_type_ ) != 1)
    {
        ERROR_MSG( "EntityType::init: class %s does not derive from BigWorld.Entity.\n",
            currDesc.name().c_str() );
    }
    else
    {
        // 4. 校验 .def 里声明的 client 方法是否都在类里实现了
        currDesc.checkMethods( currDesc.client().internalMethods(), pClass );

        // 5. 绑定：EntityType 持有 (EntityDescription, PyTypeObject*)
        EntityType * pType = new EntityType( currDesc, pModule, (PyTypeObject *)pClass );
        s_types_[ currDesc.clientIndex() ] = pType;
    }
}
```

这就是 BigWorld 的 **「按名约定」**：实体类型 `Avatar` 对应：

- `entities.xml` 里一条 `<Avatar>` 条目
- `defs/Avatar.def` 描述属性与方法
- `scripts/client/Avatar.py` 里 `class Avatar(BigWorld.Entity): ...`
- `scripts/base/Avatar.py` 里 `class Avatar(BigWorld.Base): ...`
- `scripts/cell/Avatar.py` 里 `class Avatar(BigWorld.Entity): ...`

三份 `.py` 文件可以同名（因为放在不同目录、`sys.path` 不同），各自继承不同的 C++ 基类，但共享同一份 `.def` 元数据。`EntityType::init` 还会调用 `checkMethods` 校验 `.def` 声明的方法是否在 Python 类里都实现了——这是 **「契约式编程」**：`.def` 是接口契约，`.py` 是实现。

cellapp 与 baseapp 的 `EntityType::init` 流程类似，只是导入路径与基类不同。`hasCellScript_` / `hasBaseScript_` / `hasClientScript_` 标志决定某种实体在哪些进程上有脚本——例如纯 client 实体（`isClientOnlyType()`）不会在服务端创建。

## 8. Entity 对象模型：cellapp / baseapp / client 三态

BigWorld 的 Entity 是 **三态对象**：同一个逻辑实体（如玩家「Alice」）在 cellapp、baseapp、client 上各有一个 C++ + Python 实例，三者通过 MailBox 互相引用。三态的 C++ 类不同，但都继承自 `PyInstancePlus`：

### 8.1 cellapp 的 Entity

```cpp
 *  of a "real" Entity that lives on an adjacent cell.

{
```

cellapp 的 `Entity` 持有 `RealEntity`（真实态）或被 ghost 化（幽灵态）。它的 `.def` 里 `CELL_DATA` 域的属性只存在于 cellapp 实例上。Python 脚本里 `self.position`、`self.setAoIRadius()` 等都是 cellapp 专属。

[baseapp/Base](file:///workspace/src/server/baseapp/base.hpp) 是 **代理态**——负责持久化、客户端连接、跨 cell 调度：

### 8.4 三态对比

| 维度 | cellapp Entity | baseapp Base | client Entity |
|---|---|---|---|
| C++ 基类 | `PyInstancePlus` | `PyInstancePlus` | `PyInstancePlus` |
| Python 基类 | `BigWorld.Entity` | `BigWorld.Base` | `BigWorld.Entity` |
| `.def` 域 | `CELL_DATA` | `BASE_DATA` | `CLIENT_DATA` / `OTHER_CLIENT_DATA` |

| 持久化 | 否 | 是（`writeToDB`） | 否 |

| 物理模拟 | 是 | 否 | 玩家本地物理 |

## 9. 实体的创建：placement-new 让 C++ 对象「就是」Python 对象

BigWorld 实体创建最精妙的设计是：**C++ 对象与 Python 对象是同一块内存**。这通过 Python 的 `PyType_GenericAlloc` + C++ 的 placement-new 实现。以 client 端为例（[entity_type.cpp](file:///workspace/src/client/entity_type.cpp) 第 524 行）：

```cpp
// /workspace/src/client/entity_type.cpp
Entity * EntityType::newEntity( EntityID id, Vector3 & pos,
    float * pAuxVolatile, int enterCount, BinaryIStream & data,
    StreamContents contents, Entity * pSister )
{
    // 1. 用 Python 的类对象分配内存（调用 tp_alloc，引用计数初始化为 1）
    PyObject * pObject = PyType_GenericAlloc( pClass_, 0 );

    // 2. 从网络流解出初始属性字典
    PyObject * pInitDict = this->newDictionary( data, contents );

    // 3. 补齐缺失的 OTHER_CLIENT_DATA 属性为默认值
    for (uint i=0; i < description_.propertyCount(); i++)
    {
        DataDescription * pDD = description_.property(i);
        if (pDD->isOtherClientData())
        {
            if (PyDict_GetItemString( pInitDict, pDD->name().c_str() ) == NULL)
            {
                PyObjectPtr pValue = pDD->pInitialValue();
                PyDict_SetItemString( pInitDict, pDD->name().c_str(),
                    pValue.getObject() );
            }
        }
    }

    // 4. placement-new：在 pObject 指向的内存上构造 C++ Entity
    return new (pObject) Entity(
        *this, id, pos, pAuxVolatile, enterCount, pInitDict, pSister );
}
```

关键点：

1. **`PyType_GenericAlloc(pClass_, 0)`**：`pClass_` 是用户 Python 类（如 `Avatar`）。CPython 根据 `tp_basicsize` / `tp_itemsize` 分配足够大的内存。由于 `Avatar` 继承自 `BigWorld.Entity`（即 C++ 的 `Entity::s_type_`），`tp_basicsize` 至少是 `sizeof(Entity)`，所以分配的内存装得下 C++ `Entity`。
2. **`new (pObject) Entity(...)`**：placement-new 在已分配的内存上调用 `Entity` 构造函数。`Entity` 构造函数里 `Py_InstanceHeader` 展开的初始化会正确设置 `ob_type` 与引用计数——它们已经在 `PyType_GenericAlloc` 里被设好了，构造函数不能覆盖。
3. **构造函数接收 `pInitDict`**：这个字典里的键值就是 `.def` 里声明的 `CLIENT_DATA` / `OTHER_CLIENT_DATA` 属性的初始值，会被填进 Python 实例的 `__dict__`，让脚本的 `__init__` 能读到。

这样产生的对象：

- C++ 指针 `Entity*` 与 Python 指针 `PyObject*` 指向同一地址。
- Python 脚本里 `self.position` 走 `Entity::pyGet_position`（C++ 实现）。
- C++ 代码里 `pEntity->position()` 直接访问 C++ 字段。
- Python 的引用计数归零时，`_tp_dealloc` 调用 `delete static_cast<Entity*>(pObj)`，触发 `Entity` 析构。

服务端（cellapp/baseapp）的实体创建流程类似：`Base::init` 接收 `pDict`，`Entity` 在 cellapp 上由 `EntityType::newEntity` 创建。区别是服务端实体可能从 DB 恢复（`isRestore=true`）或从别的 cellapp 迁移过来（offload）。

## 10. DataType：Python ↔ 二进制流的 Marshalling

远程方法调用与属性同步都要求把 Python 对象序列化成二进制流、再反序列化回来。这套 marshalling 体系的中心是 [DataType](file:///workspace/src/lib/entitydef/data_type.hpp) 抽象基类：

```cpp
// /workspace/src/lib/entitydef/data_type.hpp
class DataType : public ReferenceCount
{
public:
    virtual void setDefaultValue( DataSectionPtr pSection ) = 0;
    virtual PyObjectPtr pDefaultValue() const = 0;
    virtual bool isSameType( PyObject * pValue ) = 0;

    // Python 对象 → 二进制流
    virtual bool addToStream( PyObject * pValue, BinaryOStream & stream,
        bool isPersistentOnly ) const = 0;

    // 二进制流 → Python 对象
    virtual PyObjectPtr createFromStream( BinaryIStream & stream,
        bool isPersistentOnly ) const = 0;

    // Python 对象 → XML DataSection（用于编辑器、DB XML 模式）
    virtual bool addToSection( PyObject * pNewValue, DataSectionPtr pSection ) const = 0;
    virtual PyObjectPtr createFromSection( DataSectionPtr pSection ) const = 0;

    // 流 ↔ Section 互转（用于 DB 落库）
    virtual bool fromStreamToSection( BinaryIStream & stream,
        DataSectionPtr pSection, bool isPersistentOnly ) const = 0;
    virtual bool fromSectionToStream( DataSectionPtr pSection,
        BinaryOStream & stream, bool isPersistentOnly ) const = 0;

    virtual void addToMD5( MD5 & md5 ) const = 0;
    virtual bool operator<( const DataType & other ) const = 0;
};
```

`DataType` 是 **类型系统的根**，每种 BigWorld 类型都有一个 `DataType` 派生类。`addToStream` 与 `createFromStream` 是网络序列化的核心。

### 10.1 类型实现

`data_types.hpp` 定义了具体的 `DataType` 派生类：

| DataType 派生类 | 对应 .def 类型 | Python 对应 |
|---|---|---|
| `StringDataType` | `STRING` | `str` |
| `UnicodeStringDataType` | `UNICODE_STRING` | `unicode` |
| `SequenceDataType` | `ARRAY` / `TUPLE` | `list` / `tuple` |
| `IntDataType` / `FloatDataType` 等 | `INT8`...`INT64` / `FLOAT32` 等 | `int` / `float` |
| `VectorDataType` | `VECTOR3` / `VECTOR4` | `Vector3` / `Vector4` |
| `MatrixDataType` | `MATRIX` | `Matrix` |
| `ArrayDataType` / `TupleDataType` | `ARRAY` / `TUPLE` | `list` / `tuple` |
| `FixedDictDataType` | `FIXED_DICT` | 自定义 Python 类型 |
| `UserDataType` | `USER_TYPE` | 用户定义类型 |

`SequenceDataType` 是 `ArrayDataType` 与 `TupleDataType` 的基类，处理元素遍历与边界检查：


### 10.2 MetaDataType 与注册

`SimpleMetaDataType<DATATYPE>` 是模板，构造时调用 `MetaDataType::addMetaType(this)` 把自己注册到全局元类型表。`EntityDescription::parse` 解析 `.def` 时，遇到 `<Type>VECTOR3</Type>` 就查表得到 `MetaDataType`，再调 `getType(pSection)` 产出具体的 `DataType` 实例。

这套注册机制是 **可扩展的**——引擎自己的 `PatrolPath`、`UserDataObject` 等都通过 `SIMPLE_DATA_TYPE(TYPE, NAME)` 宏注册自己的数据类型。

### 10.3 Script::setData / getData：基本类型桥

`DataType` 处理的是 `.def` 里声明的「业务类型」。对于 C++ 内建类型（`int`、`float`、`Vector3`、`std::string`……），`Script::setData(PyObject*, T&, name)` 与 `Script::getData(const T&)` 提供更轻量的转换。它们被 `PY_WRITABLE_ATTRIBUTE_SET` 等宏大量使用，让属性宏能直接绑定到 C++ 成员变量。

`Script::getData` 还有针对 `EntityMailBoxRef` 的特化（见 [mailbox_base.hpp](file:///workspace/src/lib/entitydef/mailbox_base.hpp) 第 121 行）：

```cpp
namespace Script
{
    int setData( PyObject * pObj, EntityMailBoxRef & mbr, const char * varName = "" );
    PyObject * getData( const EntityMailBoxRef & mbr );
}
```

这让 MailBox 能像普通值一样在属性表与流之间穿梭——见第 13 节。

## 11. DataDescription 与 EntityDataFlags：决定数据流向

[DataDescription](file:///workspace/src/lib/entitydef/data_description.hpp) 描述单个属性，它把一个 `DataType` 与一组 **流向标志** 绑定：

```cpp
// /workspace/src/lib/entitydef/data_description.hpp
enum EntityDataFlags
{
    DATA_GHOSTED        = 0x01,  // 同步到 ghost 实体
    DATA_OTHER_CLIENT   = 0x02,  // 发给其它客户端
    DATA_OWN_CLIENT     = 0x04,  // 发给自己的客户端
    DATA_BASE           = 0x08,  // 发给 base
    DATA_CLIENT_ONLY    = 0x10,  // 纯客户端静态数据
    DATA_PERSISTENT     = 0x20,  // 持久化到 DB
    DATA_EDITOR_ONLY    = 0x40,  // 仅编辑器读写
    DATA_ID             = 0x80   // DB 中的索引列
};
```

这些标志决定了 **一个属性的改变会触发哪些网络流量**。例如 `DATA_GHOSTED | DATA_OTHER_CLIENT` 的属性变化，会同时同步到 ghost 实体和所有看到它的客户端。

`DataDescription` 的核心方法都委托给 `DataType`：

```cpp

    int             detailLevel_;       // LoD 层级
    // ...

```

### 11.1 三种索引的含义

`DataDescription` 维护多个索引，反映了 BigWorld 的多视图数据组织：

- `index_`：全局唯一索引，用于 `.def` 内部寻址。
- `localIndex_`：进程本地属性值数组的下标。每个进程只关心自己域的属性，所以 cellapp 的 `Entity` 有一个 `cellProps_` 数组，baseapp 的 `Base` 有一个 `baseProps_` 数组，按 `localIndex_` 寻址。
- `eventStampIndex_`：事件戳向量下标。`DATA_GHOSTED` 等属性需要带「最后变化时间戳」，用于增量同步与重传。
- `clientServerFullIndex_`：客户端↔服务端协议里的属性编号。

### 11.2 addSectionToStream / readStreamToDict：分域序列化

`EntityDescription` 提供按域序列化整组属性的方法：

```cpp
// /workspace/src/lib/entitydef/entity_description.hpp
bool addSectionToStream( DataSectionPtr pSection, BinaryOStream & stream,
            int dataDomains ) const;
bool readStreamToDict( BinaryIStream & stream, int dataDomains,
            PyObject * pDest ) const;
bool addDictionaryToStream( PyObject * pDict, BinaryOStream & stream,
            int dataDomains ) const;
```

`dataDomains` 参数（取 `BASE_DATA` / `CLIENT_DATA` / `CELL_DATA` / `ONLY_PERSISTENT_DATA` 等组合）决定哪些属性被序列化。例如 `writeToDB` 时传 `ONLY_PERSISTENT_DATA`，只写持久化属性；创建 cell 实体时传 `CELL_DATA`，只传 cell 域属性。

这套机制让 **同一份属性元数据能服务多种网络场景**——创建实体、属性增量同步、DB 持久化、ghost 同步都复用 `DataDescription` 与 `DataType` 的序列化能力。

## 12. MethodDescription：方法的元数据与 callMethod

[MethodDescription](file:///workspace/src/lib/entitydef/method_description.hpp) 描述一个远程方法。它持有参数类型列表与返回值类型列表：

```cpp
// /workspace/src/lib/entitydef/method_description.hpp
class MethodDescription
{
public:
    enum Component { CLIENT, CELL, BASE };

    bool parse( DataSectionPtr pSection, Component component );

    bool areValidArgs( bool exposedExplicit, PyObject * args,
        bool generateException ) const;

    // Python args → 二进制流（发送侧）
    bool addToStream( bool isFromServer, PyObject * args,
        BinaryOStream & stream ) const;

    // 二进制流 → Python 调用（接收侧）
    bool callMethod( PyObject * self, BinaryIStream & data,
        EntityID sourceID = 0, int replyID = -1,
        const Mercury::Address* pReplyAddr = NULL,
        Mercury::NetworkInterface * pInterface = NULL ) const;

    PyObjectPtr getArgsAsTuple( BinaryIStream & data,
        EntityID sourceID = 0, int replyID = -1, ... ) const;

    bool isExposed() const           { return !!(flags_ & IS_EXPOSED); }
    Component component() const      { return Component(flags_ & 0x3); }

    MethodIndex internalIndex() const  { return MethodIndex( internalIndex_ ); }
    MethodIndex exposedIndex() const   { return MethodIndex( exposedIndex_ ); }
private:
    std::string                name_;
    uint8                      flags_;
    typedef std::vector< DataTypePtr > Args;
    Args                       args_;
    typedef std::pair< std::string, DataTypePtr > ReturnValue;
    std::vector< ReturnValue > returnValues_;
    int                        internalIndex_;     // 服务端内部编号
    int                        exposedIndex_;      // 客户端↔服务端编号
    int                        exposedSubIndex_;
    float                      priority_;
};
```

### 12.1 Component 与 exposed

每个方法属于三个域之一：`CLIENT`、`CELL`、`BASE`。`Component` 标志方法定义在 `.def` 的哪个段（`<CellMethods>` / `<BaseMethods>` / `<ClientMethods>`）。

`IS_EXPOSED` 标志（在 `.def` 里写 `<Flags>CELL_PUBLIC</Flags>` 等触发）表示这个方法 **能被客户端跨网络调用**。只有 exposed 方法才有 `exposedIndex_`——它是客户端↔服务端协议里的方法编号，比 `internalIndex_` 更紧凑（服务端内部所有方法都用 `internalIndex_`，但只把 exposed 的子集暴露给客户端，节省带宽并提升安全性）。

### 12.2 addToStream：发送侧

`addToStream(isFromServer, args, stream)` 把 Python `args` 元组按 `args_` 列表的类型逐个序列化进 `stream`：

1. 校验 `args` 长度与类型（`areValidArgs`）。
2. 对每个参数，用对应 `DataType::addToStream` 写入流。
3. `isFromServer` 影响某些细节（如客户端调用服务端时，第一个参数可能是 source EntityID）。

### 12.3 callMethod：接收侧

`callMethod(self, data, sourceID, replyID, ...)` 是接收侧的核心：

1. 用 `getArgsAsTuple` 从 `data` 反序列化出 Python 参数元组（可能前置一个 source ID）。
2. 用 `PyObject_CallMethod` 或类似机制调用 `self.<methodName>(args)`——这里 `self` 是目标实体的 Python 对象。
3. 处理返回值（如果有 `returnValues_`），把返回值序列化进 reply bundle。

这就是远程方法调用的 **接收终点**：网络消息抵达后，cellapp/baseapp 找到目标 `Entity`/`Base`，再通过 `MethodDescription::callMethod` 把流还原成 Python 调用。

### 12.4 EntityMethodDescriptions

`EntityDescription` 持有三个 `EntityMethodDescriptions`（`cell_` / `base_` / `client_`），分别管理三域方法。`findClientMethod` / `findCellMethod` / `findBaseMethod` 按名查找——`PyEntityMailBox::pyGetAttribute` 与 `PyServer::pyGetAttribute` 都靠它们把方法名解析成 `MethodDescription`，再包装成 `RemoteEntityMethod`（见第 14 节）。

## 13. MailBox：跨进程引用的 Python 表达

[PyEntityMailBox](file:///workspace/src/lib/entitydef/mailbox_base.hpp) 是 **跨进程引用** 在 Python 里的表达。它的注释：

`PyEntityMailBox` 是抽象基类，每个进程有自己的具体实现：

### 13.1 进程特定的子类

以 cellapp 的 `CellEntityMailBox` 为例（[cellapp/mailbox.hpp](file:///workspace/src/server/cellapp/mailbox.hpp)）：

### 13.2 EntityMailBoxRef：可序列化的引用

`PyEntityMailBox` 本身是 Python 对象，不能直接进网络流。它的可序列化形式是 `EntityMailBoxRef`——一个 POD 结构，包含 component 类型、地址、EntityID、EntityTypeID。`Script::setData` / `getData` 对 `EntityMailBoxRef` 的特化让 mailbox 能像普通属性一样被序列化。

### 13.3 registerMailBoxComponentFactory

`PyEntityMailBox::registerMailBoxComponentFactory` 是个注册机制：每个进程启动时把 `Cell` / `Base` / `Client` 三种 component 的工厂函数注册进去，`constructFromRef` 根据流里的 component 字段选对应工厂产出具体的 mailbox 子类。这就是为什么同一个 `EntityMailBoxRef` 在不同进程上能还原成不同的 `PyEntityMailBox` 派生类。

### 13.4 ServerEntityMailBox 的迁移与失效

`ServerEntityMailBox` 还处理 **baseapp 崩溃后的地址迁移**：

## 14. RemoteEntityMethod：远程方法调用的对象化

[RemoteEntityMethod](file:///workspace/src/lib/entitydef/remote_entity_method.hpp) 是 BigWorld 远程调用语法的核心。它的注释：

> This class implements a simple helper Python type. Objects of this type are used to represent methods that the base can call on another script object (e.g. the cell, the client, or another base).

```cpp
// /workspace/src/lib/entitydef/remote_entity_method.hpp
class RemoteEntityMethod : public PyObjectPlus
{
    Py_Header( RemoteEntityMethod, PyObjectPlus )
public:
    RemoteEntityMethod( PyEntityMailBox * pMailBox,
            const MethodDescription * pMethodDescription,
            PyTypePlus * pType = &s_type_ ) :
        PyObjectPlus( pType ),
        pMailBox_( pMailBox ),
        pMethodDescription_( pMethodDescription )
    {
    }

    PY_METHOD_DECLARE( pyCall )

private:
    SmartPointer< PyEntityMailBox >     pMailBox_;
    const MethodDescription *           pMethodDescription_;
};
```

### 14.1 工作原理

当脚本写 `self.cell.foo(1, 2, 3)` 时，发生的是：

1. `self.cell` 取得一个 `CellEntityMailBox`（Python 对象）。
2. `.foo` 触发 `CellEntityMailBox::pyGetAttribute("foo")`，它调用 `findMethod("foo")` 从 cell 域的 `EntityMethodDescriptions` 找到 `MethodDescription`。
3. `findMethod` 命中后，`pyGetAttribute` 不是返回一个普通属性，而是 new 一个 `RemoteEntityMethod(pMailBox=this, pMethodDescription=foo)` 返回。
4. `(1, 2, 3)` 触发 `RemoteEntityMethod::pyCall(args)`——这是 `PY_METHOD_DECLARE(pyCall)` 生成的。
5. `pyCall` 内部调用 `pMailBox_->getStream(*pMethodDescription_)` 取得一个 `BinaryOStream`，再用 `pMethodDescription_->addToStream(...)` 把 args 序列化进去，最后 `pMailBox_->sendStream()` 发送。
6. Mercury 把 bundle 投递到目标进程，目标进程的接口处理器找到目标实体，调用 `MethodDescription::callMethod(self, data, ...)` 还原成 Python 调用。

**这就是 BigWorld 远程调用的对象化**：每个 `(mailbox, method)` 对被封装成一个可调用的 `RemoteEntityMethod` 对象，让远程调用在语法上与本地调用无异。

### 14.2 PyServer：客户端的 RemoteEntityMethod 来源

客户端没有 `PyEntityMailBox`（它不直接发 Mercury 消息），但有等价的 [PyServer](file:///workspace/src/client/py_server.hpp)：

```cpp
// /workspace/src/client/py_server.hpp
/*~ class BigWorld.PyServer
 *  A PyServer is the device through which an entity is able to call methods
 *  on it's instance on a server. BigWorld creates two PyServer objects
 *  as attributes for each client entity, "cell" and "base", which can be
 *  used to send method calls to the entity's cell and base instances,
 *  respectively.
 *
 *  PyServer objects have no default attributes or methods, however BigWorld
 *  populates them with ServerCaller objects which represent the methods that
 *  can be called.
 */
class PyServer : public PyObjectPlus
{
    Py_Header( PyServer, PyObjectPlus )
public:
    PyServer( Entity * pEntity, const EntityMethodDescriptions & methods,
        bool isProxyCaller, PyTypePlus * pType = &PyServer::s_type_ );
    PyObject * pyGetAttribute( const char * attr );
    // ...
private:
    Entity * pEntity_;
    const EntityMethodDescriptions & methods_;
    bool isProxyCaller_;
};
```

`PyServer` 持有一个 `Entity*` 与一组 `EntityMethodDescriptions`（cell 域或 base 域）。`pyGetAttribute` 按方法名查找，命中后返回一个 `ServerCaller`（功能类似 `RemoteEntityMethod`），调用它会把参数塞进客户端→服务端的 bundle（通过 `ServerConnection`）。客户端的 `Entity` 在创建时由 `BigWorld` 注入两个 `PyServer`：`self.cell` 与 `self.base`。

`isProxyCaller_` 区分「玩家自己客户端的调用」（走 own-client 协议）与「代理别的实体的调用」（走 other-client 协议）。

## 15. 远程方法调用的完整时序

把前面几节串起来，一次从 base 脚本调用 cell 方法的完整时序：

```
┌─ baseapp（Base 脚本） ─────────────────────────────────────────────┐
│  self.cell.onHit(damage=10)                                        │
│      │                                                             │
│      ▼  pyGetAttribute("cell")                                     │
│  Base::pCellEntityMailBox_ (CellEntityMailBox)                     │
│      │                                                             │
│      ▼  pyGetAttribute("onHit")                                    │
│  CellEntityMailBox::findMethod("onHit")                            │
│      → EntityDescription::cell().find("onHit")                     │
│      → MethodDescription*                                          │
│  new RemoteEntityMethod(mailbox, methodDesc)                       │
│      │                                                             │
│      ▼  pyCall( (10,) )                                            │
│  RemoteEntityMethod::pyCall                                        │
│      │                                                             │
│      ▼  pMailBox_->getStream(methodDesc)                           │
│  CellEntityMailBox::getStreamEx                                    │
│      → Mercury::Channel::bundle()                                  │
│      → 写入 exposedIndex/methodIndex + EntityID                    │
│      │                                                             │
│      ▼  methodDesc->addToStream( isFromServer=true, args, stream ) │
│  MethodDescription::addToStream                                   │
│      → 对每个 arg 调 DataType::addToStream                         │
│      │                                                             │
│      ▼  pMailBox_->sendStream()                                    │
│  Mercury 发送 bundle 到 cellapp 地址                              │
└────────────────────────────────────────────────────────────────────┘
                              │ Mercury 网络
                              ▼
┌─ cellapp（Entity 接收） ───────────────────────────────────────────┐
│  cellapp_interface 收到消息                                        │
│      → 按 methodIndex 路由到对应的接口处理器                       │
│      → 找到目标 Entity（按 EntityID）                              │
│      │                                                             │
│      ▼  MethodDescription::callMethod( pEntity, data, sourceID )   │
│  MethodDescription::getArgsAsTuple( data, sourceID )               │
│      → 对每个 arg 调 DataType::createFromStream                    │
│      → 得到 Python tuple (10,)                                     │
│  PyObject_CallMethod( pEntity, "onHit", "(O)", args )              │
│      │                                                             │
│      ▼  Entity 的 Python 派生类 Avatar.onHit(self, 10)             │
│  执行用户脚本                                                      │
└────────────────────────────────────────────────────────────────────┘
```

关键设计点：

1. **方法编号的两种含义**：发送侧写的是 `exposedIndex_`（如果是客户端发起）或 `internalIndex_`（服务端间）。接收侧根据编号查回 `MethodDescription`。
2. **sourceID 透传**：调用方把自己的 EntityID 作为 sourceID 传过去，接收方在 `getArgsAsTuple` 里把它前置成第一个参数（如果方法声明了 `ENTITY_ID` 参数）——这让被调用方知道「谁叫的我」。
3. **replyID 与返回值**：如果方法有返回值，`callMethod` 会用 `replyID` 与 `pReplyAddr` 把返回值序列化成 reply bundle 发回去。这支撑了有返回值的远程调用（虽然 MMO 里通常用回调避免阻塞）。
4. **DataType 复用**：参数序列化复用 `DataType::addToStream` / `createFromStream`——属性同步与方法调用共享同一套 marshalling，没有重复造轮子。

### 15.1 客户端→服务端的特殊路径

客户端的 `PyServer` 不走 Mercury 的 server 接口，而是走 `ServerConnection` 的 client→baseapp 通道。`PyServer` 内部把方法编号与参数塞进 `baseappExtInterface` 的 `clientMsg` bundle，baseapp 收到后按 `exposedIndex_` 路由到对应 `Base` 的方法。这条路径有额外的鉴权——只有 `IS_EXPOSED` 标志的方法才能被客户端调用，防止客户端调用服务端内部方法。

## 16. ScriptTimers：BigWorld.addTimer 的实现

[ScriptTimers](file:///workspace/src/lib/server/script_timers.hpp) 是服务端 `BigWorld.addTimer` 的底层实现。它管理一组带脚本 ID 的定时器：

```cpp
// /workspace/src/lib/server/script_timers.hpp
class ScriptTimers
{
public:
    typedef int32 ScriptID;

    static void init( EntityApp & app );
    static void fini( EntityApp & app );

    ScriptID addTimer( float initialOffset, float repeatOffset, int userArg,
            TimerHandler * pHandler );
    bool delTimer( ScriptID timerID );

    void releaseTimer( TimerHandle handle );
    void cancelAll();

    void writeToStream( BinaryOStream & stream ) const;   // 备份用
    void readFromStream( BinaryIStream & stream,
            uint32 numTimers, TimerHandler * pHandler );  // 恢复用

    ScriptID getIDForHandle( TimerHandle handle ) const;
private:
    typedef std::map< ScriptID, TimerHandle > Map;
    Map map_;
};
```

### 16.1 与 EntityApp 的关系

`ScriptTimers::init(EntityApp&)` 把全局 `g_pApp` 指针保存起来，让 `ScriptTimers` 能访问 `EntityApp::timeQueue()`——这是 BigWorld 的定时器队列（`TimeQueue`）。每个 `Base` / `Entity` 持有自己的 `ScriptTimers*`（如 `Base::pTimers_`），但所有定时器都注册在 `EntityApp` 的全局 `timeQueue` 上，由主 tick 循环统一调度。

### 16.2 addTimer 的实现

```cpp
// /workspace/src/lib/server/script_timers.cpp
ScriptTimers::ScriptID ScriptTimers::addTimer( float initialOffset,
        float repeatOffset, int userArg, TimerHandler * pHandler )
{
    int hertz = EntityAppConfig::updateHertz();
    int initialTicks = GameTime( g_pApp->time() + initialOffset * hertz );
    int repeatTicks = 0;
    if (repeatOffset > 0.f)
    {
        repeatTicks = GameTime( repeatOffset * hertz );
        if (repeatTicks < 1) repeatTicks = 1;
    }

    TimerHandle timerHandle = g_pApp->timeQueue().add(
            initialTicks, repeatTicks, pHandler, (void *)userArg );

    if (timerHandle.isSet())
    {
        int id = this->getNewID();
        map_[ id ] = timerHandle;
        return id;
    }
    return 0;
}
```

`ScriptTimers` 把脚本层的「秒」换算成 tick 数（`updateHertz` 通常是 10Hz），再注册到 `TimeQueue`。`userArg` 是脚本传入的用户数据（一个 int），会被原样传回 `TimerHandler::handleTimeout`——`Base` / `Entity` 各自的 `TimerHandler`（如 `BaseTimerHandler`）在回调里把这个 `userArg` 传给脚本的 `onTimer(self, timerID, userArg)`。

### 16.3 ScriptID 与 TimerHandle 的分离

`ScriptTimers` 维护 `ScriptID → TimerHandle` 的映射。`ScriptID` 是给脚本看的（连续的小整数，脚本拿它来 `delTimer`），`TimerHandle` 是 `TimeQueue` 内部的句柄。这种分离让脚本能用稳定的 ID 管理定时器，而底层 `TimeQueue` 的实现细节（句柄可能被复用）不暴露给脚本。

### 16.4 持久化与恢复

`writeToStream` / `readFromStream` 让定时器能跟随实体一起备份：

```cpp
// /workspace/src/lib/server/script_timers.cpp
void ScriptTimers::writeToStream( BinaryOStream & stream ) const
{
    stream << uint32( map_.size() );
    Map::const_iterator iter = map_.begin();
    while (iter != map_.end())
    {
        TimeQueue::TimeStamp time; TimeQueue::TimeStamp interval; void * pUser;
        g_pApp->timeQueue().getTimerInfo( iter->second, time, interval, pUser );
        stream << iter->first << time << interval << int32( uintptr(pUser) );
        ++iter;
    }
}
```

`Base::writeBackupData` 会调用 `ScriptTimersUtil::writeToStream(pTimers_, stream)`，把定时器写进 backup 流。当 baseapp 崩溃、备份 baseapp 接管时，`readFromStream` 重建定时器——脚本的 `onTimer` 不会因为 baseapp 切换而丢失（详见第 20 篇）。同样地，`archive` 写 DB 时不写定时器（定时器是非持久化状态），但 `writeBackupData` 写备份时写定时器——**archive 与 backup 序列化的内容不同**。

### 16.5 ScriptTimersUtil 惰性创建

`ScriptTimersUtil::addTimer(ScriptTimers** ppTimers, ...)` 接受指向指针的指针：

```cpp
// /workspace/src/lib/server/script_timers.cpp
ScriptTimers::ScriptID addTimer( ScriptTimers ** ppTimers,
    float initialOffset, float repeatOffset, int userArg,
    TimerHandler * pHandler )
{
    ScriptTimers *& rpTimers = *ppTimers;
    if (rpTimers == NULL) rpTimers = new ScriptTimers;  // 惰性创建
    return rpTimers->addTimer( initialOffset, repeatOffset, userArg, pHandler );
}
```

`Base::pTimers_` 初始为 NULL，只有第一次 `addTimer` 时才创建 `ScriptTimers` 对象——节省无定时器实体的内存。`releaseTimer` 在最后一个定时器取消时 `delete rpTimers; rpTimers = NULL;`，回归 NULL 状态。

客户端的 Entity 生命周期由服务端驱动。`ServerConnection`（[server_connection.cpp](file:///workspace/src/lib/connection/server_connection.cpp)）处理三类消息：

### 17.1 enterAoI：实体进入 AOI

### 17.2 createEntity：实体的完整数据

```cpp
// /workspace/src/lib/connection/server_connection.cpp
void ServerConnection::createEntity( BinaryIStream & rawStream )
{
    CompressionIStream stream( rawStream );  // 解压
    EntityID id; EntityTypeID type;
    Vector3 pos; int8 cyaw, cpitch, croll;
    stream >> id >> type >> pos >> cyaw >> cpitch >> croll;

    EntityID vehicleID = this->getVehicleID( id );

```

`createEntity` 携带实体的完整初始化数据：类型、位置、朝向（用 int8 压缩）、以及剩余流里的属性字典。它把剩余流交给 `EntityManager::onEntityCreate`。

### 17.3 EntityManager::onEntityCreate：创建 Python Entity

[entity_manager.cpp](file:///workspace/src/client/entity_manager.cpp) 第 260 行：

```cpp
// /workspace/src/client/entity_manager.cpp
void EntityManager::onEntityCreate( EntityID id, EntityTypeID type,
    SpaceID spaceID, EntityID vehicleID, const Position3D & position,
    float yaw, float pitch, float roll, BinaryIStream & data )
{
    Entity * pNewEntity;
    Entities::iterator iter;

    // 1. 如果实体已在缓存（之前 enterAoI 但还没创建），取出并更新
    if ((iter = cachedEntities_.find( id )) != cachedEntities_.end())
    {
        pNewEntity = iter->second;
        cachedEntities_.erase( iter );
        pNewEntity->updateProperties( data, /*callSetMethod:*/false );
        pNewEntity->pos( pos, auxFilter, 3 );
    }
    // 2. 如果实体已进入（重复 createEntity），当作更新
    else if ((iter=enteredEntities_.find( id )) != enteredEntities_.end())
    {
        pNewEntity = iter->second;
        pNewEntity->updateProperties( data, /*callSetMethod:*/true );
    }
    // 3. 否则真正创建实体
    else
    {
        EntityType * pEntityType = EntityType::find( type );
        int enterCount = unknownEntities_[id].count;
        Entity * pSister = !enteredEntities_.empty() ?
            enteredEntities_.begin()->second :
            !cachedEntities_.empty() ? cachedEntities_.begin()->second : NULL;

        // 调用第 9 节描述的 placement-new 创建
        pNewEntity = pEntityType->newEntity( id, pos, auxFilter, enterCount,
            data, EntityType::TAGGED_CELL_ENTITY_DATA, pSister );
    }

    // 检查前置资源（模型、贴图），可能延迟 enterWorld
    bool prereqsSatisfied = pNewEntity->checkPrerequisites();
    if (!prereqsSatisfied)
    {
        cachedEntities_[ id ] = pNewEntity;
        prereqEntities_.push_back( pNewEntity );
    }
    // ...
}
```

关键设计：

1. **三态处理**：缓存命中、已进入、全新创建三种情况分别处理，保证消息乱序时不重复创建。
2. **`pSister`**：传入一个已存在的实体作为「姐妹」，用于共享资源（如玩家和 NPC 用同一套模型时，可以复用模型加载）。
3. **前置资源检查**：`checkPrerequisites` 把模型/贴图加载丢到后台线程（`PrerequisitesOrder : public BackgroundTask`），加载完成后再 `enterWorld`。这避免了一次性创建大量实体时主线程卡顿。
4. **`updateProperties(callSetMethod)`**：从流里读属性填进 Python `__dict__`，并决定是否触发脚本的 `set_<prop>` 回调——首次创建不触发，更新时触发。

### 17.4 实体进入世界

资源加载完成后，`Entity::enterWorld` 被调用：

```cpp
// /workspace/src/client/entity.hpp
void enterWorld( SpaceID spaceID, EntityID vehicleID, bool transient );
```

`enterWorld` 把实体加进 `ChunkSpace`，挂载模型，触发脚本的 `onEntityEnterWorld` 回调。`leaveWorld` 与 `destroy` 对应退出与销毁。这三个回调是客户端实体生命周期在脚本层的体现。

### 17.5 leaveAoI：实体离开

```cpp
// /workspace/src/lib/connection/server_connection.cpp
void ServerConnection::leaveAoI( BinaryIStream & stream )
{
    EntityID id; stream >> id;
    if (controlledEntities_.erase( id ))
        pHandler_->onEntityControl( id, false );  // 失去控制权
    // 读取属性时间戳，用于后续重连时增量恢复
    CacheStamps stamps( stream.remainingLength() / sizeof(EventNumber) );
    // ...
    pHandler_->onEntityLeave( id, stamps );
}
```

`leaveAoI` 通知 `EntityManager` 销毁实体（或缓存起来等待可能的重入）。携带的 `EventNumber` 时间戳记录了客户端最后一次看到的属性变化编号——重连时服务端据此决定哪些变化需要重传。

### 17.6 属性更新与 volatile 数据

除了 `createEntity`，`ServerConnection` 还处理 `propertyUpdate`（属性增量更新）与 `detailedPosition`（位置 volatile 更新）。前者用 `EntityDescription::readStreamToDict` 把流还原成属性变化，触发脚本的 `set_<prop>`；后者走 `Filter`（位置滤波器），不直接调脚本。这就是为什么客户端实体的 `.def` 属性会「自动更新」——底层是 `DataDescription` + `DataType` 的反序列化。

## 18. 脚本热重载：reloadScript

BigWorld 支持运行时热重载实体脚本，这对 MMO 运营至关重要（不停机修 bug、调数值）。`EntityType` 提供了 `reloadScript` / `migrate` 接口（参见 [cellapp/entity_type.hpp](file:///workspace/src/server/cellapp/entity_type.hpp) 与 [baseapp/entity_type.hpp](file:///workspace/src/server/baseapp/entity_type.hpp)）：

```cpp
// /workspace/src/server/cellapp/entity_type.hpp
class EntityType : public ReferenceCount
{
public:
    static bool init( bool isReload = false );
    static bool reloadScript( bool isRecover = false );
    static void migrate( bool isFullReload = true );
    static void cleanupAfterReload( bool isFullReload = true );
    // ...
private:
    static EntityTypes s_curTypes_, s_newTypes_;
    static PyObject * s_pInitModules_, * s_pNewModules_;
    EntityTypePtr pOldSelf_;
};
```

### 18.1 重载流程

1. **`reloadScript`**：对每个 EntityType，用 `PyImport_ReloadModule` 重新导入 `.py` 模块，取得新的 `PyTypeObject`。构造一批新的 `EntityType`（`s_newTypes_`），与旧的（`s_curTypes_`）通过 `pOldSelf_` 链接。
2. **`migrate`**：遍历所有现存实体实例，把它们的 `ob_type` 从旧类换成新类（`swizzleClass`）。这利用了 CPython 允许运行时改 `ob_type` 的特性——只要新旧类的 `tp_basicsize` 兼容。
3. **`cleanupAfterReload`**：确认所有实例都已迁移后，释放旧 `EntityType` 与旧模块。

客户端的 [entity_type.cpp](file:///workspace/src/client/entity_type.cpp) 第 238 行 `EntityType::reload` 有类似实现：

```cpp
// /workspace/src/client/entity_type.cpp
bool EntityType::reload()
{
    for (uint i = 0; i < s_types_.size(); i++)
    {
        EntityType & et = *s_types_[i];
        PyObject * pReloadedModule = PyImport_ReloadModule( et.pModule_ );
        if (pReloadedModule == NULL) { PyErr_PrintEx(0); continue; }
        et.pModule_ = pReloadedModule;
        if (et.pClass_ != NULL) et.swizzleClass( et.pClass_ );
        if (et.pPlayerClass_ != NULL) et.swizzleClass( et.pPlayerClass_ );
    }
    return true;
}
```

### 18.2 swizzleClass：换类型不改实例

`swizzleClass` 把旧类的所有实例的 `ob_type` 改成新类。这之所以可行，是因为 Entity 实例的内存布局由 C++ `Entity` 类决定（`tp_basicsize`），与 Python 派生类无关——派生类只增加方法与类属性，不改实例字段布局。所以换 `ob_type` 后，实例的 C++ 字段不变，但调用的 Python 方法变成新版本。

### 18.3 Personality 重载

`Personality::callOnInit(isReload=true)` 让人格模块知道这是一次重载——人格脚本可以据此决定是否重新初始化全局状态。`EntityType::init(isReload=true)` 与首次 init 的区别也在于跳过某些一次性初始化。

### 18.4 限制

热重载的限制：

- **`.def` 不能变**：`EntityDescription` 在启动时解析，运行时不重新解析。改 `.def` 需要重启进程。
- **C++ 类不能变**：`Entity` / `Base` 的 C++ 字段布局固定，热重载只换 Python 类。
- **实例状态保留**：实例的 `__dict__` 在重载后保留，但类属性的默认值变化不会反向影响已有实例。

- **事件戳与重传**：`DATA_GHOSTED` 属性的 `eventStampIndex_`、`EventNumber`、`PropertyEventStamps` 如何支撑可靠增量同步与客户端重连后的状态对齐。

- **Pickler**：跨进程 Python 对象 pickle 的实现（`Pickler::init`、`pyPickleReduce`），以及与 `EntityMailBoxRef` 的关系。
- **客户端实体过滤**：`Filter` 派生类（`KalmanFilter` 等）如何平滑位置更新，以及 `detailedPosition` 消息的处理。

### 19.3 设计哲学小结

BigWorld 的脚本与对象模型体现了几个一以贯之的设计哲学：

1. **C++ 是骨架，Python 是血肉**：性能敏感的基础设施（网络、调度、空间索引、序列化）用 C++，业务逻辑用 Python。两者通过 `PyObjectPlus` 共享同一块内存，零拷贝互访。
2. **元数据驱动**：`.def` 是单一事实来源，属性/方法的流向、持久化、暴露性全由元数据决定，C++ 代码与 Python 脚本都基于同一份 `EntityDescription` 工作。
3. **位置透明**：`self.cell.foo()` 与 `self.bar` 语法一致，前者是跨进程 RPC，后者是本地访问。`MailBox` + `RemoteEntityMethod` 把远程调用对象化，让脚本无需关心网络细节。
4. **进程对称、对象模型统一**：cellapp / baseapp / client 三态共享 `EntityID`、`.def`、`DataType`，差异只在 C++ 类与持有的 MailBox。这让「同一逻辑实体的三态视图」自然耦合。
5. **可热重载**：脚本与对象模型分离设计，让 `ob_type` 可换、实例状态可留，支撑 MMO 不停机迭代。

这些设计让 BigWorld 能在「百万实体 + 千级并发」的规模下，仍保持脚本层的简洁与可迭代性——这是 MMO 引擎最难的部分，也是 BigWorld 最核心的工程价值。
