## 1. 问题背景：崩溃不丢数据

MMO 服务端进程众多：每个 baseapp / cellapp 都持有大量实体状态在内存里。任何一个进程都可能因硬件故障、bug、OOM 而崩溃。BigWorld 必须保证：

- **玩家持久数据不丢**：装备、等级、任务进度等写进 DB，崩溃后能从 DB 恢复。
- **在线玩家不掉线**：baseapp 崩溃时，其上的 base 实体（含玩家连接 Proxy）能由备份 baseapp 接管，客户端重连后继续游戏。
- **世界状态可恢复**：cellapp 崩溃时，其上的 cell 由 cellappmgr 重新分配，base 实体重新创建对应的 real。

为此 BigWorld 设计了三道防线：

| 防线 | 机制 | 周期 | 目的 |
|---|---|---|---|
| 持久化 | `writeToDB` → dbmgr → MySQL | 按需 / 定期 | 落盘，长期保存 |
| 归档（Archive） | baseapp 周期把所有 base 写 dbmgr | 周期（archivePeriod） | 兜底，防止长期未写库的 base 丢失 |
| 备份（Backup） | baseapp 实时把 base 镜像到另一 baseapp | 每 tick（分批） | baseapp 崩溃时秒级接管 |

## 2. 持久化的三层架构

```
┌─────────────────────────────────────────────────────────────┐
│  Entity 级（baseapp 内）                                      │
│  Base::writeToDB / Base::archive                             │
│  序列化 ONLY_PERSISTENT_DATA 域 → 打包成 stream              │
└──────────────────────────┬──────────────────────────────────┘
                           │ DBInterface::writeEntity / loadEntity
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  baseapp 级                                                  │
│  Archiver(周期归档)  BackupSender(实时备份)  SqliteDatabase(二级库)│
│  WorkerThread(异步写 dbmgr)                                  │
└──────────────────────────┬──────────────────────────────────┘
                           │ Mercury 消息
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  dbmgr 级                                                    │
│  Database → IDatabase(MySQLDatabase / XmlDatabase)           │
│  Consolidator(合并二级库)  EntityAutoLoader(启动恢复加载)     │
└──────────────────────────┬──────────────────────────────────┘
                           │ SQL
                           ▼
                      ┌─────────┐
                      │  MySQL  │
                      └─────────┘
```

三层各有侧重：entity 级负责「序列化什么」，baseapp 级负责「何时写、写哪、备份到哪」，dbmgr 级负责「怎么落库、怎么合并」。

## 3. dbmgr：数据库抽象层 IDatabase

### 3.1 IDatabase 接口

[dbmgr](file:///workspace/src/server/dbmgr/) 的核心是 [Database](file:///workspace/src/server/dbmgr/database.hpp) 单例，它通过 [IDatabase](file:///workspace/src/lib/dbmgr_lib/idatabase.hpp) 抽象底层存储，支持 MySQL 与 XML 两种实现（`src/lib/dbmgr_mysql/`、`src/lib/dbmgr_xml/`）。`IDatabase` 的注释说：

> This class defines an interface to the database. This allows us to support different database types (such as XML or MySQL). Many functions in this interface are asynchronous i.e. return results through callbacks.

关键接口（节选自 idatabase.hpp）：

```cpp
// /workspace/src/lib/dbmgr_lib/idatabase.hpp
class IDatabase
{
public:
    virtual bool startup( const EntityDefs& entityDefs,
            Mercury::EventDispatcher & dispatcher, bool isFaultRecovery ) = 0;
    virtual bool shutDown() = 0;

    virtual BillingSystem * createBillingSystem() = 0;

    // 读实体
    struct IGetEntityHandler { /* onGetEntityComplete(isOK, entityKey, pBaseLoc) */ };
    virtual void getEntity( const EntityDBKey & entityKey, BinaryOStream * pStream,
            bool shouldGetBaseEntityLocation, const char * pPasswordOverride,
            IGetEntityHandler & handler ) = 0;

    // 写实体
    struct IPutEntityHandler { /* onPutEntityComplete(isOK, dbID) */ };
    virtual void putEntity( const EntityKey & entityKey, EntityID entityID,
            BinaryIStream * pStream, const EntityMailBoxRef * pBaseMailbox,
            bool removeBaseMailbox, UpdateAutoLoad updateAutoLoad,
            IPutEntityHandler & handler ) = 0;

    // 删实体
    struct IDelEntityHandler { /* onDelEntityComplete(isOK) */ };
    virtual void delEntity( const EntityDBKey & ekey, EntityID entityID,
            IDelEntityHandler& handler ) = 0;

    // 二级库
    virtual void addSecondaryDB( const SecondaryDBEntry& entry ) = 0;
    virtual void updateSecondaryDBs( const BaseAppIDs& ids,
            IUpdateSecondaryDBshandler& handler ) = 0;
    virtual void getSecondaryDBs( IGetSecondaryDBsHandler& handler ) = 0;
    virtual int clearSecondaryDBs() = 0;

    // 启动恢复：把上次受控关机时活跃的实体重新加载
    virtual void autoLoadEntities( IEntityAutoLoader & autoLoader ) = 0;

    // 重映射 mailbox（baseapp 死亡时把 DB 里指向死地址的 mailbox 改到活地址）
    virtual void remapEntityMailboxes( const Mercury::Address& srcAddr,
            const BackupHash & destAddrs ) = 0;

    virtual bool lockDB() = 0;   // 独占锁，启动时自动锁
    virtual bool unlockDB() = 0;
};
```

注意几乎所有操作都是**异步回调**式（`IGetEntityHandler`/`IPutEntityHandler` 等），因为 MySQL 查询在 dbmgr 的后台线程执行，结果通过回调回传。实现可以选择在返回前就调回调（同步语义），但调用方无需区分。

## 4. MySQL 实现：MySQLDatabase / Table / Transaction

`src/lib/dbmgr_mysql/` 是 IDatabase 的 MySQL 实现。核心类：

| 类 | 文件 | 职责 |
|---|---|---|
| `MySQLDatabase` | [mysql_database.hpp](file:///workspace/src/lib/dbmgr_mysql/mysql_database.hpp) | `IDatabase` 的 MySQL 实现，管理连接池、表结构 |
| `Table` | [table.hpp](file:///workspace/src/lib/dbmgr_mysql/table.hpp) | 一张实体表，含列定义与 property mapping |
| `TableSynchroniser` | [table_synchroniser.hpp](file:///workspace/src/lib/dbmgr_mysql/table_synchroniser.hpp) | 把 entitydef 的属性定义同步成表结构（建表/改表） |
| `TableInspector` | [table_inspector.hpp](file:///workspace/src/lib/dbmgr_mysql/table_inspector.hpp) | 检查表结构一致性 |
| `Query` / `ResultSet` | [query.hpp](file:///workspace/src/lib/dbmgr_mysql/query.hpp) / [result_set.hpp](file:///workspace/src/lib/dbmgr_mysql/result_set.hpp) | SQL 查询封装与结果集 |
| `Transaction` | [transaction.hpp](file:///workspace/src/lib/dbmgr_mysql/transaction.hpp) | 事务 |
| `LockedConnection` | [locked_connection.hpp](file:///workspace/src/lib/dbmgr_mysql/locked_connection.hpp) | 从连接池借出并加锁的连接 |
| `MySQLBillingSystem` | [mysql_billing_system.hpp](file:///workspace/src/lib/dbmgr_mysql/mysql_billing_system.hpp) | 计费系统实现 |

### 4.1 属性到列的映射

`mappings/` 子目录把 entitydef 的每种 `DataType` 映射成 MySQL 列：

- `string_mapping`、`unicode_string_mapping`、`unique_id_mapping`
- `num_mapping`（整数/浮点）
- `blob_mapping`（二进制大对象，常用于序列化的复杂属性）
- `vector_mapping`、`sequence_mapping`、`composite_property_mapping`、`class_mapping`
- `user_type_mapping`、`udo_ref_mapping`（用户数据对象引用）
- `timestamp_mapping`

`entity_mapping` 把一个 entity 类型映射成一张表，`property_mappings_per_type` 管理每类实体的属性映射集合。

### 4.2 后台任务

dbmgr 的 MySQL 操作放在后台线程，由 `tasks/` 下的 `BackgroundTask` 派生类执行：

- `put_entity_task`（写实体）
- `get_entity_task`（读实体）
- `del_entity_task`（删实体）
- `get_ids_task`/`put_ids_task`（ID 分配）
- `add_secondary_db_entry_task`/`get_secondary_dbs_task`/`update_secondary_dbs_task`（二级库）
- `get_base_app_mgr_init_data_task`（启动初始化数据）
- `set_game_time_task`/`write_space_data_task`/`execute_raw_command_task`

这些任务通过 `BgTaskManager`（见 [sqlite_database.hpp](file:///workspace/src/server/baseapp/sqlite_database.hpp) 的 `BgTaskManager bgTaskMgr_`，dbmgr 同理）在后台线程跑，完成后回调到主线程。这就是 dbmgr 异步语义的实现。

## 5. Entity 级读写：writeToDB / loadFromDB

### 5.1 持久化域 ONLY_PERSISTENT_DATA

[EntityDescription](file:///workspace/src/lib/entitydef/entity_description.hpp) 把属性按域划分。`DataDescription` 的 `DATA_PERSISTENT` 标志（见 [data_description.hpp](file:///workspace/src/lib/entitydef/data_description.hpp)）标记某属性要进 DB。`writeToDB`/`loadFromDB` 只序列化带 `DATA_PERSISTENT` 的属性（即 `ONLY_PERSISTENT_DATA` 域），不序列化 volatile（位置/朝向）、不序列化 `DATA_OTHER_CLIENT` 等运行时属性。

### 5.2 Base::writeToDB

[Base](file:///workspace/src/server/baseapp/base.hpp) 是 baseapp 上 base 实体的 C++ 类，提供 `writeToDB`：

```cpp
// /workspace/src/server/baseapp/base.hpp
class Base: public PyInstancePlus
{
public:
    bool writeToDB( int8 flags, WriteToDBReplyHandler * pHandler = NULL,
            PyObjectPtr pCellData = NULL );
    bool writeToDB( int8 flags, WriteToDBReplyStructPtr pReplyStruct,
            PyObjectPtr pCellData );
    bool requestCellDBData( int8 flags, WriteToDBReplyStructPtr pReplyStruct );

    void autoArchive();
    bool archive();

    void writeBackupData( BinaryOStream & stream, bool isOffload );
    void offload( const Mercury::Address & dstAddr );
    void readBackupData( BinaryIStream & stream );

    PY_KEYWORD_METHOD_DECLARE( py_writeToDB )   // 暴露给 Python: self.writeToDB(...)
    // ...
};
```

`writeToDB(flags)` 的 `flags` 区分写 base 数据 / cell 数据 / 注销（logOff）。如果需要 cell 数据，先通过 `requestCellDBData` 向 cellapp 请求 cell 实体的持久化属性（cellapp 上的 `RealEntity::writeBackupData` 配合，见 [real_entity.hpp](file:///workspace/src/server/cellapp/real_entity.hpp) 的 `writeBackupProperties`），收到后合并进 stream 再发给 dbmgr。

Python 侧用法：

```python
# base 脚本里
self.writeToDB( True )   # 落库，可带回调
```

### 5.3 WriteToDBReply：回调协调

[WriteToDBReplyStruct](file:///workspace/src/server/baseapp/write_to_db_reply.hpp) 协调「写库完成」与「备份完成」两个异步事件：

```cpp
// /workspace/src/server/baseapp/write_to_db_reply.hpp
class WriteToDBReplyHandler
{
public:
    virtual void onWriteToDBComplete( bool succeeded ) = 0;
};

class WriteToDBReplyStruct : public ReferenceCount
{
public:
    WriteToDBReplyStruct( WriteToDBReplyHandler * pHandler );
    void onWriteToDBComplete( bool succeeded );   // dbmgr 回执
    void onBackupComplete();                       // 备份 baseapp 回执
private:
    bool succeeded_;
    bool backedUp_;
    bool writtenToDB_;
    WriteToDBReplyHandler * pHandler_;
};
```

注释明确：它在「entity 已写盘」且（可选）「已备份到 backup baseapp」后才回调 `pHandler`。这保证调用方知道数据已双重安全。

## 6. 写库流程的完整时序

下面是 `self.writeToDB()` 从 Python 到 MySQL 的完整跨模块时序：

```
 Python(base)        BaseApp(Base)        WorkerThread        DBMgr(Database)      MySQL
     │                   │                     │                    │                 │
     │ 1. self.writeToDB │                     │                    │                 │
     │──py_writeToDB────>│                     │                    │                 │
     │                   │ 2. 序列化 ONLY_PERSISTENT_DATA            │                 │
     │                   │    (若需 cell 数据, requestCellDBData     │                 │
     │                   │     -> cellapp 回 cell 持久属性)           │                 │
     │                   │ 3. 构造 WriteToDBReplyStruct              │                 │
     │                   │    打 DBInterface::writeEntity bundle     │                 │
     │                   │ 4. 投递到 WorkerThread (异步)              │                 │
     │                   │──submit job────────>│                    │                 │
     │                   │                     │ 5. WorkerJob::operator()              │
     │                   │                     │    发 writeEntity 消息                 │
     │                   │                     │──writeEntity──────>│                 │
     │                   │                     │                    │ 6. Database::writeEntity
     │                   │                     │                    │    新建 WriteEntityHandler
     │                   │                     │                    │    -> IDatabase::putEntity
     │                   │                     │                    │       (MySQLDatabase)
     │                   │                     │                    │ 7. 后台 PutEntityTask
     │                   │                     │                    │──SQL INSERT/UPDATE─>│
     │                   │                     │                    │<──OK──────────────│
     │                   │                     │                    │ 8. onPutEntityComplete
     │                   │                     │                    │    回执 writeEntity reply
     │                   │                     │<──reply────────────│                 │
     │                   │                     │ 9. WorkerJob 回调到主线程              │
     │                   │<──onWriteToDBComplete─────────────────────│                 │
     │                   │ 10. WriteToDBReplyStruct::onWriteToDBComplete                │
     │                   │     (若需备份, 等 onBackupComplete)        │                 │
     │                   │ 11. pHandler->onWriteToDBComplete(true)   │                 │
     │<──return True────│                     │                    │                 │
     │  (Python 回调或返回)                    │                    │                 │
```

关键点：

- **WorkerThread**（[worker_thread.hpp](file:///workspace/src/server/baseapp/worker_thread.hpp)）是 baseapp 内的异步线程，把 `writeEntity` 消息发到 dbmgr，避免阻塞主 tick。`WorkerJob` 是抽象任务，`operator()` 返回下次调度间隔，返回 `<0` 表示不再调度。
- **WriteEntityHandler**（[write_entity_handler.hpp](file:///workspace/src/server/dbmgr/write_entity_handler.hpp)）在 dbmgr 侧承载一次写库的状态，实现 `IPutEntityHandler`/`IDelEntityHandler`，完成后 `finalise` 回复 baseapp。
- 写库是**增量**的：`putEntity` 接收 `EntityKey` + 属性 stream，MySQL 侧用 `put_entity_task` 做 INSERT 或 UPDATE（按 `dbID` 是否已存在）。

### 6.1 加载流程

加载是反向：`loadEntity` 消息到 dbmgr → [LoadEntityHandler](file:///workspace/src/server/dbmgr/load_entity_handler.hpp)（继承 `GetEntityHandler`）→ `IDatabase::getEntity` → `get_entity_task` 读 MySQL → `onGetEntityCompleted` 回 baseapp。`LoadEntityHandler` 还实现 `Database::ICheckoutCompletionListener`：如果实体已被 checkout（即已在线），会发 `sendAlreadyCheckedOutReply`，避免重复加载。

## 7. baseapp 级：归档（Archive）

### 7.1 Archiver

[Archiver](file:///workspace/src/server/baseapp/archiver.hpp) 负责周期性地把本 baseapp 上所有 base 实体写库，注释说：

> This class is responsible for periodically archiving this BaseApp's entities.

```cpp
// /workspace/src/server/baseapp/archiver.hpp
class Archiver
{
public:
    Archiver();
    void tick( DBMgr & dbMgr, BaseAppMgrGateway & baseAppMgr,
        Bases & bases, SqliteDatabase * pSecondaryDB );
    void handleBaseAppDeath( const Mercury::Address & addr,
        Bases & bases, SqliteDatabase * pSecondaryDB );
    static bool isEnabled();
private:
    void restartArchiveCycle( Bases & bases );
    int                  archiveIndex_;          // 当前周期进度
    std::vector<EntityID> basesToArchive_;       // 本周期待归档列表
    Mercury::Address     deadBaseAppAddr_;       // 死亡 baseapp 地址(触发其备份归档)
};
```

### 7.2 归档周期

`tick` 每个 game tick 调用，按 `archivePeriodInTicks` 把所有 base 分摊到多个 tick 上归档（不是一次性全写，避免突发负载）。`basesToArchive_` 是本周期要归档的实体列表，每 tick 处理 `offloadPerTick_` 个。

对每个待归档的 base，调用 `Base::autoArchive()` → `Base::archive()` → `writeToDB`。归档与显式 `writeToDB` 走同一条链路（第 6 节）。

### 7.3 二级库优先

注意 `tick` 的参数里有 `SqliteDatabase * pSecondaryDB`：如果启用了二级库（第 10 节），归档会优先写到本机 SQLite，而不是直接打 dbmgr，从而减轻 dbmgr 压力。`handleBaseAppDeath` 时会把死亡 baseapp 备份过来的实体也纳入归档。

## 8. baseapp 级：备份（Backup）与哈希环

### 8.1 BackupSender

[BackupSender](file:///workspace/src/server/baseapp/backup_sender.hpp) 负责把本 baseapp 的 base 实体**实时**备份到其它 baseapp：

```cpp
// /workspace/src/server/baseapp/backup_sender.hpp
class BackupSender
{
public:
    void tick( const Bases & bases, Mercury::NetworkInterface & networkInterface );
    Mercury::Address addressFor( EntityID entityID ) const
    {
        return entityToAppHash_.addressFor( entityID );   // 哈希定位备份目标
    }
    void setBackupBaseApps( BinaryIStream & data, ... );  // baseappmgr 下发新哈希
    void handleBaseAppDeath( const Mercury::Address & addr );
    void restartBackupCycle( const Bases & bases );
    bool autoBackupBase( Base & base, Mercury::BundleSendingMap & bundles, ... );
    bool backupBase( Base & base, Mercury::BundleSendingMap & bundles, ... );
private:
    int    offloadPerTick_;
    float  backupRemainder_;
    std::vector<EntityID> basesToBackUp_;
    BackupHash entityToAppHash_;       // 当前生效的哈希
    BackupHash newEntityToAppHash_;    // 正在切换到的新哈希
    bool   isUsingNewBackup_;
    bool   isOffloading_;
};
```

`addressFor(entityID)` 用 `BackupHash` 把 entity ID 哈希到某个备份 baseapp 地址。`tick` 每 tick 分批备份 `basesToBackUp_` 里的实体（每 tick `offloadPerTick_` 个，`backupRemainder_` 处理小数溢出）。

### 8.2 BackupHash：一致性哈希

[BackupHash](file:///workspace/src/lib/server/backup_hash.hpp) 是一致性哈希，注释说：

> This class is used to hash an entity id to an address of a BaseApp. The hash function handles changing hash sizes nicely. It attempts to keep most values hashing to the same bucket.

```cpp
// /workspace/src/lib/server/backup_hash.hpp
class MiniBackupHash
{
public:
    uint32 hashFor( EntityID id ) const;     // (id * prime_) % virtualSize_
private:
    uint32 prime_;        // 随机素数，使不同 baseapp 哈希分布不同
    uint32 size_;         // 实际桶数(=baseapp 数)
    uint32 virtualSize_;  // >= size_ 的 2 的幂，用于取模
};

class BackupHash : public MiniBackupHash
{
public:
    Mercury::Address addressFor( EntityID id ) const;
    class DiffVisitor { onAdd / onChange / onRemove };
    void diff( const BackupHash & other, DiffVisitor & visitor );   // 比较新旧哈希差异
private:
    std::vector< Mercury::Address > addrs_;
};
```

`prime_` 是随机素数，作用是「一旦几个 baseapp 死亡，哈希分布也不会全挤一起」。`virtualSize_` 取 `>= size_` 的 2 的幂，让取模高效。`diff` 用 `DiffVisitor` 模式通知「哪些 entity 的备份地址 add/change/remove」，便于 baseappmgr 增量下发新哈希。

### 8.3 BackupHashChain：死亡历史

[BackupHashChain](file:///workspace/src/lib/server/backup_hash_chain.hpp) 记录哈希变更历史，用于 baseapp 死亡时定位「该实体的备份现在在哪」：

```cpp
// /workspace/src/lib/server/backup_hash_chain.hpp
class BackupHashChain
{
public:
    void adjustForDeadBaseApp( const Mercury::Address & deadApp,
                               const BackupHash & hash );
    Mercury::Address addressFor( const Mercury::Address & address,
                                 EntityID entityID ) const;
private:
    typedef std::map< Mercury::Address, BackupHash > History;
    History history_;   // 每个曾经死亡的 baseapp 地址 -> 当时的哈希
};
```

当 baseapp X 死亡，`adjustForDeadBaseApp` 把「X 死亡时的哈希」存进 `history_`。后续查某 entity 的备份地址时，`addressFor` 会沿历史链回溯，正确路由到接管 X 的 baseapp。这是环形备份能跨越多次崩溃仍正确定位的关键。

### 8.4 BackedUpBaseApp：本机持有的备份

[BackedUpBaseApp](file:///workspace/src/server/baseapp/backed_up_base_app.hpp) 存「本 baseapp 作为别人备份」所持有的实体数据：

```cpp

{
public:

    bool erase( EntityID entityID );

    void restoreRemotely( const Mercury::Address & deadAddr,
          const BackupHashChain & backedUpHashChain );

    typedef std::map< EntityID, std::string > Container;

class BackedUpBaseApp
{

    void switchToNewBackup();     // 新哈希就绪后切换
```

## 9. 归档 vs 备份：区别与协作

| 维度 | 归档（Archive） | 备份（Backup） |
|---|---|---|
| 类 | `Archiver` | `BackupSender` + `BackedUpBaseApp` |
| 目标 | dbmgr（→ MySQL）或二级库 | 另一个 baseapp 的内存 |
| 频率 | 周期性（`archivePeriod`，分摊到多 tick） | 每 tick（分批，实时） |
| 数据形态 | 持久化属性 stream | 完整 base 备份数据（含运行时状态） |
| 用途 | 长期落盘兜底 | baseapp 崩溃时秒级接管 |
| 失败影响 | 短期无影响（下次归档补） | baseapp 崩溃时该实体可能丢未归档进度 |

两者协作：备份保证「活体不丢」（崩溃即接管），归档保证「落盘不丢」（即使所有 baseapp 都崩，DB 里仍有最近归档）。`WriteToDBReplyStruct` 同时等 `onWriteToDBComplete`（归档）和 `onBackupComplete`（备份），就是这种协作的体现。

`AutoBackupAndArchive::Policy`（[auto_backup_and_archive.hpp](file:///workspace/src/lib/server/auto_backup_and_archive.hpp)）控制每个 base 的策略：

```cpp
// /workspace/src/lib/server/auto_backup_and_archive.hpp
namespace AutoBackupAndArchive
{
enum Policy
{
    NO = 0,         // 不自动备份/归档
    YES = 1,        // 自动
    NEXT_ONLY = 2,  // 只在下一次
};
}
```

`RealEntity` 持有 `shouldAutoBackup_`（[real_entity.hpp](file:///workspace/src/server/cellapp/real_entity.hpp)），`Base` 也有对应策略，脚本可按实体类型配置。

## 10. 二级库（Secondary DB）：SQLite 缓存

### 10.1 动机

dbmgr（MySQL）是单点且较慢。如果每个 baseapp 归档都直打 dbmgr，dbmgr 会成为瓶颈。BigWorld 允许每个 baseapp 配一个本机 **SQLite 二级库**，把离线/低频 entity 的归档先写本地 SQLite，再由 dbmgr 周期性合并（consolidate）到主库，大幅减轻 dbmgr 压力。

### 10.2 SqliteDatabase

[SqliteDatabase](file:///workspace/src/server/baseapp/sqlite_database.hpp) 是 baseapp 内的 SQLite 接口：

```cpp
// /workspace/src/server/baseapp/sqlite_database.hpp
class SqliteDatabase
{
public:
    SqliteDatabase( const std::string & filename, const std::string & dir );
    bool init( const std::string & checksum );
    void writeToDB( DatabaseID & dbID, EntityTypeID typeID, GameTime & time,
            MemoryOStream & stream, WriteToDBReplyStructPtr pReplyStruct ) const;
    void commit();
    void commitBgTask( Transaction * pTrans, bool shouldFlip );
    void commitFgTask( Transaction * pTrans );
    void tick();
private:
    sqlite3 * pCon_;
    const std::string path_;
    const std::string * pCurrTable_;
    bool shouldFlip_;          // 双表翻转
    TransactionPool transPool_;
    Transaction * pTrans_;
    BgTaskManager bgTaskMgr_;  // 后台提交
    const std::string flipTable_;
    const std::string flopTable_;
    // ...
};
```

特点：

- **双表翻转（flip/flop）**：用 `flipTable_`/`flopTable_` 两张表交替写入。后台线程往「当前表」commit 时，前台可往另一张表写新数据，避免读写冲突。`shouldFlip_` 控制何时翻转。
- **Transaction 池**：`TransactionPool` 复用 `Transaction` 对象，`Transaction` 聚合多个 `Row`，批量 commit。
- **Row**：`Row(dbID, typeID, time, stream, replyStruct)` 是一行记录，`writeToDB(stmt)` 用预编译语句插入。
- **后台提交**：`commitBgTask` 把 commit 放到 `BgTaskManager` 后台线程，`commitFgTask` 在前台完成收尾。

### 10.3 SecondaryDBConfig

[SecondaryDBConfig](file:///workspace/src/server/baseapp/secondary_db_config.hpp) 是配置：

```cpp
// /workspace/src/server/baseapp/secondary_db_config.hpp
class SecondaryDBConfig
{
public:
    static ServerAppOption< bool > enable;
    static ServerAppOption< float > maxCommitPeriod;
    static ServerAppOption< uint > maxCommitPeriodInTicks;
    static ServerAppOption< std::string > directory;
};
```

### 10.4 二级库注册与合并

baseapp 启动时向 dbmgr 注册自己的二级库（`DBInterface::secondaryDBRegistration`，含地址、appID、location）。dbmgr 用 `IDatabase::addSecondaryDB` 记录。`Archiver::tick` 优先写二级库，`SqliteDatabase::commit` 周期性落盘。

dbmgr 侧通过 `updateSecondaryDBs`/`getSecondaryDBs`/`numSecondaryDBs`/`clearSecondaryDBs` 管理二级库条目。合并由 [Consolidator](#15-合并consolidate二级库回写主库) 完成。

## 11. 崩溃恢复：machined → reviver → 接管

### 11.1 machined 检测进程死亡

每台机器跑一个 `machined` 守护进程。它监控本机所有 BigWorld 进程（baseapp/cellapp/dbmgr/...）的心跳。进程死亡时，machined 通过 `MF_REVIVER_PING_MSG`（见各 interface 的 reviver ping）通知 reviver。

### 11.2 Reviver

[Reviver](file:///workspace/src/server/reviver/reviver.hpp) 是恢复协调进程：

```cpp
// /workspace/src/server/reviver/reviver.hpp
class Reviver : public ServerApp, public TimerHandler, public Singleton< Reviver >
{
public:
    void revive( const char * createComponent );
    bool hasEnabledComponents() const;
    virtual void handleTimeout( TimerHandle handle, void * arg );
private:
    virtual bool init( int argc, char * argv[] );
    ComponentRevivers components_;
};
```

它持有一组 [ComponentReviver](file:///workspace/src/server/reviver/component_reviver.hpp)，每个 `ComponentReviver` 监控一类组件：

```cpp
// /workspace/src/server/reviver/component_reviver.hpp
class ComponentReviver : public Mercury::ShutdownSafeReplyMessageHandler,
    public TimerHandler, public Mercury::InputMessageHandler,
    public IntrusiveObject< ComponentReviver >
{
public:
    bool activate( ReviverPriority priority );
    bool deactivate();
    virtual void handleMessage( ... );   // 死亡消息
    virtual void handleTimeout( ... );   // ping 超时
    int maxPingsToMiss() const;
    int pingPeriod() const;
private:
    const Mercury::InterfaceElement * pBirthMessage_;
    const Mercury::InterfaceElement * pDeathMessage_;
    const Mercury::InterfaceElement * pPingMessage_;
    ReviverPriority priority_;
    int pingsToMiss_;
    int maxPingsToMiss_;
    int pingPeriod_;
};
```

工作方式：

1. `ComponentReviver` 周期性 ping 被监控组件（`pPingMessage_`）。
2. 连续 `maxPingsToMiss_` 次未响应，判定死亡。
3. `revive(createParam)` 通过 machined 启动新进程（`createParam` 指定启动命令）。
4. 同时通过 `pDeathMessage_` 通知相关 manager（baseappmgr/cellappmgr）触发接管。

`ReviverPriority` 决定多个 reviver 谁先恢复（避免重复恢复）。

### 11.3 baseappmgr 的接管协调

[BaseAppMgr](file:///workspace/src/server/baseappmgr/baseappmgr.hpp) 收到 baseapp 死亡通知后：

```cpp
// /workspace/src/server/baseappmgr/baseappmgr.hpp
class BaseAppMgr : public ManagerApp, public TimerHandler, public Singleton< BaseAppMgr >
{
public:
    void handleBaseAppDeath( const BaseAppMgrInterface::handleBaseAppDeathArgs & args );
    void handleBaseAppDeath( const Mercury::Address & addr );
    bool onBaseAppDeath( const Mercury::Address & addr );
    void recoverBaseApp( ... );
    void useNewBackupHash( ... );          // 下发新哈希
    void requestBackupHashChain( ... );    // baseapp 请求哈希链
private:
    enum AdjustBackupLocationsOp
    {
        ADJUST_BACKUP_LOCATIONS_OP_ADD,
        ADJUST_BACKUP_LOCATIONS_OP_RETIRE,
        ADJUST_BACKUP_LOCATIONS_OP_CRASH
    };
    void adjustBackupLocations( const Mercury::Address & addr,
            AdjustBackupLocationsOp op );
    void checkForDeadBaseApps();
    std::auto_ptr< BackupHashChain > pBackupHashChain_;
    Mercury::Address deadBaseAppAddr_;
};
```

`onBaseAppDeath(addr)` 触发 `adjustBackupLocations(addr, CRASH)`，重新计算 `BackupHash`（去掉死地址），通过 `useNewBackupHash` 下发给所有活着的 baseapp。同时 dbmgr 收到 `handleBaseAppDeath`，调用 `IDatabase::remapEntityMailboxes(srcAddr, destAddrs)` 把 DB 里指向死 baseapp 的 mailbox 重映射到活 baseapp。

下面是 baseapp#3 崩溃、baseapp#4 接管其备份、客户端重连的完整时序：

```
    │                  │                 │                  │ 7.对有 client 的 base,         │

    │                  │                 │                  │                 │                  │
    │                  │                 │                  │                 │ 8.客户端断线重连  │
```

关键点：

- 第 3 步 `BackupHashChain` 保证 #4 知道「#3 的备份确实在我这」（即使经历了多次哈希变更）。

## 13. cellapp 崩溃恢复

cellapp 崩溃与 baseapp 不同：cellapp 上的 real 不持久化（cell 实体是运行时模拟的），但它的死亡会影响 baseapp 上的 base（base 持有指向 cell real 的 mailbox）和邻居 cellapp 上的 ghost。

### 13.1 DeadCellApps

[DeadCellApps](file:///workspace/src/server/baseapp/dead_cell_apps.hpp) 在 baseapp 上跟踪最近死亡的 cellapp：

```cpp

{

    bool isRecentlyDead( const Mercury::Address & addr ) const;
    void addApp( const Mercury::Address & addr, BinaryIStream & data );
    void tick( const Bases & bases, Mercury::NetworkInterface & intInterface );
private:
    void removeOldApps();
    typedef std::vector< shared_ptr< DeadCellApp > > Container;
    Container apps_;
    typedef std::list< shared_ptr< DyingCellApp > > DyingCellApps;

};
```

`isRecentlyDead` 让 baseapp 知道某 cellapp 刚死，避免把消息发到死地址；`tick` 推进死亡 cellapp 上 base 的 real 重建（通过 `Base::restoreTo`/`emergencySetCurrentCell` 在新 cellapp 上重建 real）。

### 13.2 cellapp 侧的清理

cellapp 侧由 [AckCellAppDeathHelper](file:///workspace/src/server/cellapp/ack_cell_app_death_helper.hpp) 协调（详见文档 19 第 14 节）：清理坏 ghost、等待 emergencySetCurrentCell 应答、确认后才 `ackCellAppDeath` 给 cellappmgr。cellappmgr 收到所有 ack 后，把死 cellapp 的 cell 重新分配（`recoverCellApp`）。

### 13.3 base 侧恢复 real

死亡的 cellapp 上每个 real 对应一个 base（在 baseapp 上活着）。baseapp 通过 `create_cell_entity_handler.hpp` 重新在活着的 cellapp 上创建 real，`Base::restoreTo(spaceID, cellAppAddr)` 完成重建。`Base::emergencySetCurrentCell` 是紧急路径，用于 cellapp 突然死亡时立即把 base 的 cell 指针改到新 cellapp。

```cpp

    virtual void start();
    virtual void abort();
    virtual void addEntity( EntityTypeID entityTypeID, DatabaseID dbID );
    virtual void onAutoLoadEntityComplete( bool isOK );
private:
    void checkFinished();
    bool sendNext();           // 分批加载，控制速率
    typedef std::vector< std::pair< EntityTypeID, DatabaseID > > Entities;
    Entities entities_;
    int numOutstanding_;
    int numSent_;
    bool hasErrors_;
};
```

`sendNext` 分批发送加载请求（避免一次性压垮 baseapp），`onAutoLoadEntityComplete` 收集结果，`checkFinished` 全部完成后通知系统恢复完成。`IDatabase::autoLoadEntities(autoLoader)` 是 dbmgr 侧入口。

## 16. 共享数据与全局 base

### 16.1 SharedDataManager

[SharedDataManager](file:///workspace/src/server/baseapp/shared_data_manager.hpp) 在 baseapp 上管理跨 baseapp 共享的数据：

```cpp
// /workspace/src/server/baseapp/shared_data_manager.hpp
class SharedDataManager
{
public:
    static shared_ptr< SharedDataManager > create( Pickler * pPickler );
    void setSharedData( BinaryIStream & data );
    void delSharedData( BinaryIStream & data );
    void addToStream( BinaryOStream & stream );
private:
    SharedData * pBaseAppData_;   // baseapp 间共享
    SharedData * pGlobalData_;    // 全局共享(跨 cellapp/baseapp)
};
```

这些数据由 baseappmgr/cellappmgr 作为权威源分发（`BaseAppMgr::setSharedData`/`delSharedData`），用于跨进程的协调状态（如全局计数、跨服信息）。

### 16.2 全局 base

`BaseAppMgr` 持有 `GlobalBases`（`std::map<std::string, EntityMailBoxRef>`，见 baseappmgr.hpp），通过 `registerBaseGlobally`/`deregisterBaseGlobally` 注册按名字全局可寻址的 base（如 `MailBox` 名字服务）。任何进程都能通过名字查到这些 base 的 mailbox。

## 17. 注意事项与未覆盖项

- **`writetodb_reply_handler` 等**：本仓库 baseapp 目录有 `write_to_db_reply.hpp`，dbmgr 侧的回执由 `WriteEntityHandler::onPutEntityComplete` 触发，经 Mercury reply 回 baseapp 的 `WorkerThread`，再回调 `WriteToDBReplyStruct`。
- **`MySQLBillingSystem` / `BillingSystem`**：计费系统是 `IDatabase::createBillingSystem` 的产物，`src/lib/dbmgr_lib/billing_system.hpp` 定义基类，`mysql_billing_system.hpp`/`custom_billing_system.hpp`/`py_billing_system.hpp` 是不同实现。本文未深入计费细节，参见 [billing_system.hpp](file:///workspace/src/lib/dbmgr_lib/billing_system.hpp)。
- **`TableSynchroniser` 的建表逻辑**：`src/lib/dbmgr_mysql/table_synchroniser.cpp` 负责把 entitydef 的属性定义同步成 MySQL 表结构（建表、加列、改类型），启动时跑一次，具体迁移算法参见该文件。
- **`MigrateMailboxVisitor` / `BaseBackupSwitchMailboxVisitor`**：任务要求中提到的 `lib/server` 这两个 visitor 类，用于遍历 mailbox 并在 baseapp 切换/迁移时重写地址，仓库中对应 `backup_hash.hpp`/`backup_hash_chain.hpp` 的 `diff`/`adjustForDeadBaseApp` 机制，精确实现参见 `lib/server` 下对应 cpp。
- **`reviver` 的 TagsHandler**：`Reviver::TagsHandler` 处理 machined 返回的机器 tag，用于决定本机该跑哪些组件，细节参见 [reviver.hpp](file:///workspace/src/server/reviver/reviver.hpp)。
- **受控关机（controlledShutDown）**：`ShutDownStage`（见各 interface）分阶段关机，保证归档完成、备份转移完成后再退出，本文未展开阶段机，参见 `baseappmgr_interface.hpp` 的 `controlledShutDown` 消息。
- **`dbmgr_xml`**：XML 实现是 MySQL 的备选（主要用于开发/测试），接口同为 `IDatabase`，本文以 MySQL 为主。
- **`Proxy::writeBackupData` / `offload`**：Proxy 作为 Base 子类，其备份/迁移走 `Base` 的通用路径，额外处理客户端连接的转移（`transferClient`/`restoreClient`），参见 [proxy.hpp](file:///workspace/src/server/baseapp/proxy.hpp)。
